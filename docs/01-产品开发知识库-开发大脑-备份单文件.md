# 产品开发知识库（开发大脑）

> **本文档的定位**：正规互联网公司从想法到上线的完整知识库。它是一份**通用文档**——只讲"产品开发这件事本身是怎么做的、有哪些环节、每个专业名词是什么意思"，**不包含任何具体产品的决策**（具体产品的内容写在各项目自己的需求文档里）。
>
> **读者**：不懂技术的产品负责人 / 独立开发者 / 任何想弄明白"开发一个产品到底要做什么"的人。
>
> **作者视角**：资深程序员，把每个环节讲透，所有专业名词都带人话解释。
>
> **使用场景**：开发任何产品（网页、桌面应用、手机 app、小程序）时，这份文档都是随时可查的"大脑"。

---

## 第 0 章：如何使用本文档

**三种读法：**

| 你想干什么 | 怎么用 |
|---|---|
| 第一次了解产品开发全貌 | 从第 1 章开始按顺序读，每章先读"人话"部分 |
| 开发中遇到一个不懂的词 | 直接查第 14 章《术语速查表》（按字母排序） |
| 想知道"这一步正规团队怎么做" | 查对应章节，看"标准做法"小节 |

**每个章节的统一结构：**
1. **是什么**——先用人话讲清楚这件事是干什么的
2. **标准做法**——正规公司是怎么做的
3. **专业名词**——本章出现的所有术语，中英对照 + 人话解释
4. **常见误区**——新手/外行最容易搞错的地方

**文中例子约定**：为了讲清楚概念，本文会使用假想产品举例（比如"假设你在做一个记账 app"）。**例子与任何真实项目无关**，你的项目该怎么做，等你我确认需求后再写进项目自己的需求文档。

## 第 1 章：一个产品是怎么诞生的——全景总览

### 1.1 八大阶段总览

一个产品从"我有一个想法"到"用户用上了"，正规公司会走过八个阶段：

```
想法
 │
 ▼
① 需求阶段 ──► 搞清楚"到底做什么"
 │
 ▼
② 设计阶段 ──► 画出来"长什么样"
 │
 ▼
③ 技术方案阶段 ──► 定好"用什么做、怎么搭"
 │
 ▼
④ 开发阶段 ──► 动手写代码
 │
 ▼
⑤ 测试阶段 ──► 检查"对不对、好不好"
 │
 ▼
⑥ 运维阶段 ──► 放到服务器上跑起来
 │
 ▼
⑦ 发布阶段 ──► 送到用户手里
 │
 ▼
⑧ 运营迭代阶段 ──► 收集反馈，做下一个版本
 │
 └──────► 回到①，开始新一轮循环
```

### 1.2 八大阶段速览表

| 阶段 | 干什么（人话） | 谁干 | 产出物 | 完事标志 |
|---|---|---|---|---|
| ① 需求 | 搞清楚：给谁用、解决什么问题、做哪些功能 | 产品经理（PM） | 需求文档（PRD） | 需求评审会通过 |
| ② 设计 | 把功能画成界面：先黑白草稿，后上色效果图 | UI/UX 设计师 | 设计稿 | 设计评审通过 |
| ③ 技术方案 | 定语言、定架构、定数据库、定接口 | 架构师/技术负责人 | 技术方案文档 | 技术评审通过 |
| ④ 开发 | 写代码：前端画界面，后端写逻辑 | 前端/后端工程师 | 代码 | 功能开发完成 |
| ⑤ 测试 | 挑毛病：零件单独测、拼起来测、整体点一遍 | 测试工程师（QA） | 测试报告 | 验收通过 |
| ⑥ 运维 | 部署到服务器、配域名、装监控、看日志 | 运维工程师（DevOps） | 线上运行的服务 | 服务稳定运行 |
| ⑦ 发布 | 打包、分发、上线，让用户拿到手 | 全员配合 | 发布版本 | 用户能下载使用 |
| ⑧ 运营迭代 | 收集用户反馈、看数据、排下一版需求 | 产品经理+运营 | 迭代计划 | 进入下一轮循环 |

> ⚠️ **重要认知**：这八个阶段不是"做完一个才做下一个"的流水线，而是会来回反复的。比如测试阶段发现需求定错了，会回到需求阶段改文档——这叫**迭代**。正规团队允许反复，但**不允许跳过**：不写需求就写代码，后面返工的成本是前者的十倍。

### 1.3 团队角色（人话版）

| 角色 | 英文/缩写 | 人话解释 |
|---|---|---|
| 产品经理 | PM（Product Manager） | "产品该做什么"的决策者。写需求文档，回答"为什么做这个功能"。注意：PM 还有另一层意思（Project Manager，项目经理），管进度排期的，别混 |
| UI 设计师 | UI Designer | 管"好不好看"：颜色、字体、按钮长什么样 |
| UX 设计师 | UX Designer | 管"好不好用"：点哪里、怎么跳转、流程顺不顺 |
| 前端工程师 | Frontend Engineer | 写用户看得见的界面部分（网页/桌面窗口里的画面） |
| 后端工程师 | Backend Engineer | 写用户看不见的逻辑部分（数据怎么存、怎么算） |
| 测试工程师 | QA（Quality Assurance） | 专门挑毛病的人，保证质量 |
| 运维工程师 | DevOps / SRE | 管服务器和线上稳定的人，"服务器医生" |
| 架构师 | Architect | 技术方案的设计者，决定"整个项目用什么技术怎么搭" |
| 全栈工程师 | Full-stack Engineer | 前端后端都会写的人 |

### 1.4 一个人 + AI 的模式，怎么映射这些角色

大公司是一群人分工，而个人项目（尤其用 AI 辅助开发）是把这些角色压缩到两个人身上：

| 角色 | 由谁承担 | 人话 |
|---|---|---|
| 产品经理 | **你** | 你定义产品：痛点、功能、优先级，AI 不做这个 |
| 设计师 | AI 出稿 + 你确认 | AI 画界面草图，你用"好不好看、顺不顺手"的感觉来验收 |
| 架构师/前后端 | AI | 技术决策和写代码由 AI 完成，但**决策过程要讲给你听** |
| 测试 | AI 自测 + 你验收 | AI 跑自动检查，你最后亲手用一遍 |
| 运维 | 平台 | 开源项目用 GitHub 托管，不需要自己租服务器 |
| 项目进度管理 | 你 + 文档 | 用"做一步记一步"的台账文档跟踪进度 |

**核心原则：产品侧的判断（做什么、好不好用）永远由你做，技术侧的实现（怎么写、怎么搭）由 AI 做，但 AI 必须把每个技术决策用人话解释到你能拍板为止。**

### 1.5 常见误区

- ❌ **"先写代码，需求后面再说"**——最贵的错误。代码改一行容易，方向错了全白写。
- ❌ **"设计就是美工"**——设计 = 交互（好不好用）+ 视觉（好不好看），一半是逻辑活。
- ❌ **"测试是最后才做的事"**——正规团队从写代码的第一天就在测试。
- ❌ **"上线就结束了"**——上线是运营迭代的开始，大多数产品死于上线后没人管。

### 1.6 单人 vibe coding 的工具链

一个人用 AI（如 Claude Code）开发产品时，工具链分成三张表：**你操作的 App、AI 操作的 CLI、AI 可接的 MCP 插件**。

**① 你（人）需要的 App：**

| 工具 | 干什么 | 装法 |
|---|---|---|
| VS Code | 看代码、验收改动、自己改两行 | 官网下载或 `brew install --cask visual-studio-code` |
| 浏览器 | 验收网页和界面效果 | 自带 |
| GitHub 网页版 | 看仓库、Issue、Release | 无需安装 |
| 终端 Terminal | 跑命令、看日志 | 系统自带 |

**② AI 需要的 CLI（命令行工具）：**

| 工具 | 干什么 | 装法 |
|---|---|---|
| Git | 版本管理（时光机） | macOS 一般自带；没有则 `xcode-select --install` |
| Node.js + npm | 跑 JS 生态（Electron/React/Vite 全靠它） | 官网安装包或 nvm |
| gh（GitHub CLI） | AI 直接操作 GitHub：建仓库、发 Release、传安装包 | `brew install gh` 然后 `gh auth login`（你登录一次） |
| Python 3 | 跑辅助脚本（批处理、图像处理等） | 官网或 `brew install python` |
| Homebrew | Mac 装软件的命令行"应用商店" | 官网一键脚本 |

**③ AI 可接的 MCP（插件，装进 Claude Code 后 AI 获得新能力）：**

| MCP | 干什么 |
|---|---|
| 搜索类（ddg-search 等） | 联网查资料、查文档 |
| GitHub MCP | 更彻底地操作 GitHub：建 repo、管 Issue/PR、发 Release |
| Playwright MCP | 自动打开网页、截图、验收界面 |
| 办公类（飞书等） | 读写办公文档、多维表格 |

**④ 不需要装的**（外行容易误装）：数据库软件（小项目 JSON 文件够用，见第 13 章）、Docker 服务器套件（单机应用不需要，见第 7 章）、Xcode 完整版（打 dmg 用 electron-builder 即可，见 5.3 节）。

**⑤ 各章提到的"环节工具"在单人 + AI 模式下谁替代谁**（避免误解"文档里提过的都要装"）：

| 文档提到的工具 | 正规团队用法 | 单人 + AI 模式 | 你要装吗 |
|---|---|---|---|
| Figma | 设计师画设计稿 | **AI 直接出设计稿/HTML 原型**，你只验收好不好看 | ❌ 不需要（想亲手调设计才装） |
| Jira / Trello / Linear | 管需求池和进度 | **双文档机制替代**：知识库（大脑）+ 项目台账（做一步记一步） | ❌ 不需要 |
| Sentry | 收集线上崩溃 | 单机应用先用本地日志；产品发布后崩溃多了再加 | ⏳ 后置 |
| Postman / Apifox | 人肉调试 API 接口 | AI 直接用代码/命令调接口 | ❌ 不需要 |
| Navicat 等数据库软件 | 可视化管数据库 | 用 JSON 文件，没有数据库 | ❌ 不需要 |
| Docker Desktop | 跑容器 | 单机应用没有容器 | ❌ 不需要 |
| Xcode | 写原生应用 | Electron 出 dmg 用 electron-builder | ❌ 不需要 |
| 图床/CDN 控制台 | 托管图片资源 | 有需要时按项目单独配（如 ImgBed） | ⏳ 按需 |

**规律**：文档 A 讲的是"正规团队完整链路"，其中凡是**纯执行类**的工具（设计、调试、接口、管理），AI 都能替代；凡是**你亲自上手**的工具（看代码的 VS Code、验收的浏览器），才需要装。

**装机口诀**：先跑起来（Node + Git），再连上云（gh + GitHub），最后按需加 MCP。

## 第 2 章：需求阶段（产品经理的世界）

### 2.1 是什么

需求阶段回答一个问题：**"我们到底要做什么？"**

把人话的"我想要个东西"变成开发团队能照着干的"合同"。这个阶段最重要的产出物是 **PRD**。

### 2.2 标准做法：PRD 详解

**PRD（Product Requirements Document，产品需求文档）** 是整个项目的"宪法"：产品经理写、开发照着做、测试照着验、扯皮时翻它。一份正规 PRD 包含八个部分：

**① 背景与目标**
- 人话：为什么做这个东西？解决谁的什么痛苦？
- 关键名词：**痛点（Pain Point）**——用户难受的地方；**目标用户（Target User）**——给谁用
- 标准写法：一句话说清"帮助____（谁）解决____（什么问题），达到____（什么效果）"

**② 用户与场景**
- 人话：用户在什么情况下会用你的产品？
- 关键名词：**使用场景（Use Case）**——"周末下午，我打开电脑想继续上周的项目，却发现找不到服务了"这种具体描述
- 标准写法：列出 3-10 个典型场景，每个场景一两句话

**③ 功能清单（按优先级）**
- 人话：要做什么功能，先做哪个后做哪个
- 关键名词：**优先级（Priority）**、**P0/P1/P2**（见 2.4）、**MVP（Minimum Viable Product，最小可行产品）**——能解决核心痛点的最少功能集，先做 MVP 是个人项目的黄金法则

**④ 页面清单与交互说明**
- 人话：有哪些界面？每个界面上有什么？点了会怎样？
- 标准写法：一页一页列——"首页：顶部一个搜索框，中间是列表，点列表项进入详情页"
- 名词见第 3 章

**⑤ 非功能需求**
- 人话：除了"有什么功能"之外的要求
- 关键词：**性能**（快不快）、**兼容性**（哪些设备能用）、**安全性**、**稳定性**
- 标准写法："应用启动时间不超过 3 秒""支持 macOS 12 以上"这类可量化的句子

**⑥ 验收标准**
- 人话：做到什么程度算"这个功能做完了"？
- 关键名词：**验收标准（Acceptance Criteria）**——可验证的完成定义
- 标准写法：每条都是"当____时，应该____"，可以被测试验证

**⑦ 里程碑**
- 人话：分几期交付？每期做什么？
- 关键名词：**里程碑（Milestone）**、**迭代（Iteration）**——一轮一轮的周期

**⑧ 明确不做**
- 人话：划边界，什么功能**这一版不做**（防止需求膨胀）
- 这是最容易被忽视也最重要的一节：写清楚"不做"比"做"更能保护项目

### 2.3 标准做法：需求评审会

PRD 写完，产品经理召集设计、开发、测试开会，逐条过 PRD：
- 开发评估"这个功能技术上可不可行、要多久"
- 测试确认"这个验收标准能不能测"
- 有争议当场拍板，改完文档再开发
- 评审会的本质：**让所有人开工前对齐同一张图纸**

### 2.4 标准做法：优先级体系

| 级别 | 含义 | 人话 | 判据 |
|---|---|---|---|
| **P0** | Must-have | 没有它产品不成立 | "没有这个功能，痛点就解决不了" |
| **P1** | Should-have | 应该有，没有也能凑合用 | "没有会难受，但能用" |
| **P2** | Could-have | 锦上添花 | "以后有精力再做" |

配套法则 **MoSCoW**：Must（必须）/ Should（应该）/ Could（可以）/ Won't（这版不做）——和 P0/P1/P2 大致对应（MoSCoW 多一级 Won't「这版不做」，P 体系里没有对应项）。

### 2.5 专业名词

| 名词 | 全称 | 人话 |
|---|---|---|
| PRD | Product Requirements Document | 产品需求文档，项目的宪法 |
| MRD | Market Requirements Document | 市场需求文档，论证"这个市场值得做"（大公司用，个人项目不需要） |
| BRD | Business Requirements Document | 商业需求文档，论证"这生意能赚钱"（大公司用） |
| 用户故事 | User Story | 用固定句式描述需求："作为一个____，我想____，以便____" |
| 验收标准 | Acceptance Criteria | "做到什么程度算完"的可验证标准 |
| MVP | Minimum Viable Product | 最小可行产品，先做最核心的 |
| 竞品分析 | Competitive Analysis | 研究市面上同类产品怎么做的，取其精华避其坑 |
| 需求变更 | Requirement Change | 开发中改需求——越晚变更代价越大 |
| 痛点 | Pain Point | 用户难受的地方 |
| 使用场景 | Use Case | 用户在什么情况下用 |
| 迭代 | Iteration | 一轮一轮的开发周期 |

### 2.6 常见误区

- ❌ **把"我想要的功能"当成"用户需要的功能"**——需求的第一来源是痛点，不是灵感。
- ❌ **PRD 写成 100 页**——个人项目 3-5 页足够，写清楚上面八节即可。
- ❌ **只写"做什么"不写"验收标准"**——没有验收标准，开发说"做完了"、测试说"没做完"，永远扯不清。
- ❌ **需求评审走形式**——评审是为了提前发现"理解不一致"，不是过场。

### 2.7 需求管理与项目管理（需求到开发的衔接）

PRD 写完不是直接扔给开发，中间还有一套"翻译和调度"的工作——**项目管理（Project Management）**：

| 名词 | 人话 |
|---|---|
| 需求池 Backlog | 所有待做功能的"排队名单"，按优先级从上往下排，做完一个划掉一个 |
| 任务拆解 Task Breakdown | 把 PRD 里一个功能拆成若干可执行的小任务（"做登录页"拆成"画界面/写校验/接接口"） |
| 排期 Scheduling | 估算每个任务要多久，排出时间表 |
| 估时 Estimation | 估算任务工时的动作（单位常用"人天"；敏捷团队用 **Story Point 故事点**——相对大小的抽象单位） |
| Sprint 冲刺 | 敏捷开发的"一个工作周期"（通常 1-2 周），周期开始时挑任务进冲刺，结束时要交付可用成果 |
| 需求管理工具 | 管 Backlog、排期、进度用的软件：**Jira**（行业标准，复杂）、**Trello**（看板式，简单）、**Linear**（新一代，简洁）、飞书多维表格（国内常用） |
| 看板 Kanban | 把任务卡片拖来拖去的可视化板子：待办 → 进行中 → 已完成 |

**为什么需要这一层？** 因为"人话的需求"和"代码的任务"粒度不同：PRD 说"做一个登录功能"，开发需要的是"今天做页面、明天做校验、后天联调"。拆解和排期就是这道翻译工序。个人项目的简化版：把 PRD 拆成里程碑清单，用台账文档跟踪"已做/待做"——这就是"做一步记一步"的由来。

## 第 3 章：设计阶段（设计师的世界）

### 3.1 是什么

设计阶段回答一个问题：**"这个东西长什么样、怎么用？"**

设计分两层，外行常混为一谈：
- **交互设计（UX）**：好不好用——按钮放哪、点一下发生什么、流程顺不顺。这是"逻辑活"
- **视觉设计（UI）**：好不好看——颜色、字体、间距、图标。这是"美学活"

正规流程：先交互后视觉，先定"怎么用"再定"长多好看"。

### 3.2 标准做法：四级进化

设计稿不是一步到位的，正规团队画四轮：

| 级别 | 名词 | 人话 | 像什么 |
|---|---|---|---|
| 第 1 级 | 线框图 Wireframe | 黑白草图，只画"哪块放什么" | 毛坯房户型图 |
| 第 2 级 | 低保真 Lo-Fi | 线框图加细节：每个按钮文字都写上 | 简装修效果图 |
| 第 3 级 | 高保真 Hi-Fi | 上色、上图标、上真实内容 | 精装修效果图 |
| 第 4 级 | 原型 Prototype | 可点击的"假应用"，能模拟操作流程 | 样板间，能走进去逛 |

个人项目的务实做法：**线框图必须画（哪怕是纸上的），高保真可以简化**。AI 时代，AI 可以根据描述直接出高保真稿，但线框图阶段"理清布局"这一步不能省。

### 3.3 设计工具

| 工具 | 人话 |
|---|---|
| Figma | 目前行业标准的设计软件（在浏览器里用），多人协作 |
| Sketch | 老牌 Mac 设计软件 |
| 即时设计/摹客 | 国内同类工具 |
| 纸和笔 | 永远不过时的第一轮工具 |

### 3.4 标准做法：设计系统（Design System）

**设计系统** = 把界面上反复出现的元素（颜色、字体、按钮、卡片）做成一套"标准件"，全产品统一使用。

- 好处：界面风格统一、改一处全改、开发不用重复造轮子
- 关键名词：**组件库（Component Library）**——按钮/输入框等标准件的集合；**设计规范（Design Spec）**——颜色值、字号、间距的规定
- 人话：就像装修公司给全小区统一的瓷砖型号和门把手款式，每家都在标准里选

### 3.5 UX 概念

| 名词 | 全称 | 人话 |
|---|---|---|
| 信息架构 | IA（Information Architecture） | 内容怎么组织：哪个页面套哪个页面、菜单怎么分 |
| 用户流程 | User Flow | 用户完成一件事要经过的路径："打开→登录→点新建→填表→保存" |
| 可用性 | Usability | 用户能不能顺利用完不卡壳 |
| 可访问性 | a11y（Accessibility） | 残障人士（如视障）也能用，屏幕朗读器等 |

| 深色模式 | Dark Mode | 深色主题，省电护眼 |
| 拖放 | Drag & Drop | 鼠标按住拖到目标处放下（拖文件进窗口、拖卡片排序），桌面应用最常用的交互之一 |

| 向导 | Wizard | 安装器/设置里"第 1 步→第 2 步→第 3 步"的分步流程页 |

### 3.8 常见误区

- ❌ **跳过线框图直接写代码**——布局问题在草图上改 1 分钟，在代码里改 1 小时。
- ❌ **设计追求"独特"忽略"熟悉"**——用户习惯了开关长什么样，就做成那样；独特留给亮点功能。
- ❌ **组件叫法不统一**——需求里说"弹窗"、设计说"Modal"、开发说"Dialog"，对不上号就返工。这就是为什么上面两张表要存在。
- ❌ **一个人拍脑袋定设计**——至少让一个"没用过的人"试一下，立刻暴露流程问题。

### 3.9 设计交付与动效

设计做完后要"交接"给开发，交接物有标准叫法：

| 名词 | 人话 |
|---|---|
| 切图 Export Assets | 把设计稿里的图标、图片导出成开发能直接用的文件 |
| 标注 Specification（Spec） | 在稿子上标清每个元素的精确尺寸、颜色值、字号——开发的"施工图" |
| 交互动效 Motion/Animation | 元素的动态效果：按钮按下的反馈、页面切换的过渡、弹窗弹出方式 |
| 动效曲线 Easing | 动效的快慢节奏（先快后慢更像物理世界） |

**个人项目务实做法**：Figma 自带标注和切图功能，开发按标注写即可；动效第一版从简，别让"炫"拖垮进度。

## 第 4 章：技术方案阶段（架构师的世界）

### 4.1 是什么

技术方案阶段回答一个问题：**"用什么技术、怎么搭？"**

需求说清了"做什么"、设计画出了"长什么样"，技术方案定"怎么做出来"。这个阶段是纯技术决策，但好架构师会把每个决策**用人话讲给非技术的人听**，因为技术方案直接影响工期、成本、以后好不好改。

### 4.2 标准做法：技术选型的三个标准

**技术选型（Technology Selection）** = 选编程语言、选框架、选数据库。正规团队用三个标准打分：

| 标准 | 人话 | 举例 |
|---|---|---|
| 生态成熟度 | 这技术有没有很多人用？出了问题搜不搜得到答案？ | 用的人多 = 坑都被人踩过了 |
| 执行者能力 | 写代码的人（团队或 AI）熟不熟这个技术？ | 会 Java 的团队硬上 Go，工期翻倍 |
| 目标平台 | 这个东西跑在什么设备上？ | 只跑苹果设备才能选 Swift；要跨平台就排除它 |

选型是**取舍**，没有"最好的技术"，只有"最适合这个项目+这批人"的技术。

### 4.3 标准做法：架构设计

**架构（Architecture）** = 代码世界的"房屋结构图"：分几层、分几块、块和块之间怎么传话。架构决定"以后改功能是动一面墙还是拆整栋楼"。

三个通用概念：

| 名词 | 人话 |
|---|---|
| 分层架构 Layered Architecture | 从上到下分层：界面层（给人看的）→ 业务层（干活的逻辑）→ 数据层（存取数据）。下层不认识上层，改界面不影响逻辑 |
| 前后端分离 Frontend/Backend Separation | 前端（界面）和后端（逻辑+数据）分成两个独立工程，靠 API 传话。好处：两边各改各的 |
| 模块化 Modularization | 按功能拆成独立小房间（模块），每个模块职责单一，坏了只修一个房间 |

反面教材：**单体架构（Monolith）** = 所有代码混在一大坨里，改一处牵全身——项目小的时候省事，大了就是灾难。**微服务（Microservices）** = 拆成几十个独立小服务各自部署——大厂才需要，个人项目用是过度设计。

### 4.4 标准做法：数据库设计

**数据库（Database）** = 专门存取数据的"仓库软件"。设计数据库 = 设计仓库里有哪些表格、每张表有哪些列。

| 名词 | 人话 |
|---|---|
| 表 Table | 一张表格（如"用户表""订单表"） |
| 字段 Field / 列 Column | 表格的一列（如"用户名""手机号"） |
| 记录 Record / 行 Row | 表格的一行（一个用户的信息） |
| 主键 Primary Key | 每行唯一的身份证号（ID） |
| 外键 Foreign Key | 指向另一张表某行的"引用"（订单表里的"用户ID"） |
| 索引 Index | 给表格建目录，查询变快（书里的目录页） |
| 关系型数据库 | MySQL、PostgreSQL 这类：表之间有明确关联，数据严格整齐 |
| 非关系型数据库（NoSQL） | MongoDB 这类：数据灵活松散，适合结构不固定的数据 |

数据量小的项目也可以不用数据库软件，直接用**文件**存数据（JSON/CSV），简单透明。

### 4.5 标准做法：API 设计

**API（Application Programming Interface，应用程序接口）** = 两个程序之间约定的"传话规则"。

人话版：你去银行柜台，只能按银行规定的格式办事（填单子、报卡号），柜台才给你办。API 就是这个"规定格式"——程序 A 按格式发请求，程序 B 按格式给回应。

| 名词 | 人话 |
|---|---|
| 请求 Request | 你发出的"我要办什么" |
| 响应 Response | 对方回的"办好了/办不了" |
| HTTP 方法 | 办事的种类：GET（查询）/ POST（新增）/ PUT（整体替换）/ PATCH（部分修改）/ DELETE（删除） |
| 状态码 Status Code | 结果的数字代号：200 成功 / 201 创建成功 / 400 你请求写得不对 / 401 没登录 / 403 没权限 / 404 找不到 / 500 服务器自己挂了 |
| RESTful | 一种流行的 API 设计风格，用"名词当网址、动词用 HTTP 方法" |
| 第三方服务集成 | 常见"接线"对象：**支付**（微信支付/支付宝/Stripe）、短信验证码、地图、第三方登录（OAuth）——都是对方提供 API，你照着接口文档接 |
| JSON | 数据交换的标准格式，长得像 `{"名字": "小明", "年龄": 30}` |
| 接口文档 API Docs | 记录所有 API 用法的说明书（工具：Swagger/OpenAPI） |

**API 设计 = 前后端的合同**：后端写好接口文档，前端照着开发，两边不必等对方——这是多人协作能并行的关键。

### 4.6 常见误区

- ❌ **技术方案追求时髦**——"别人用了新框架我也要"。选型的第一标准是"执行者熟不熟、生态成不成熟"，不是新不新。
- ❌ **架构过度设计**——10 个用户的产品按 1 亿用户设计，纯浪费。架构复杂度要配得上项目规模。
- ❌ **不做接口文档**——没有文档的 API 就是口头约定，联调时互相甩锅。
- ❌ **技术方案不翻译给人听**——技术负责人如果解释不清"为什么这么选"，这个方案大概率是拍脑袋。

## 第 5 章：开发阶段（程序员的世界）

> 这是八个阶段里的**重头戏**，也是名词最密集的一章。写代码的全部家当都在这里。

### 5.1 前端开发

**前端（Frontend）** = 用户看得见的部分：画面、按钮、动画。在网页里是网页本身，在桌面应用里是应用窗口里的界面。

#### 5.1.1 前端三件套

所有前端界面，不管多复杂，底层都是这三样：

| 技术 | 全称 | 人话 | 类比 |
|---|---|---|---|
| HTML | HyperText Markup Language | 搭骨架：标题、段落、按钮摆在哪 | 房屋的梁和墙 |
| CSS | Cascading Style Sheets | 化妆：颜色、字体、大小、间距 | 墙漆和家具 |
| JavaScript（JS） | — | 行为：点按钮发生什么、数据怎么变 | 水电开关 |

#### 5.1.2 TypeScript（TS）

**TypeScript** = JavaScript 的加强版，多了一个"**类型（Type）**"系统。

人话：JS 就像菜市场喊价，说几就是几，写错了一运行才炸；TS 给每个数据贴上"类型标签"（这个是数字、那个是字符串），**在写代码时就拦住大部分低级错误**。标签不影响运行，但让代码更稳、AI 写起来也更不易出错。

| 名词 | 人话 |
|---|---|
| 类型 Type | 数据的"身份标签"：number 数字 / string 文本 / boolean 真假 |
| 类型检查 Type Checking | 自动核对"标签对不对"的体检（工具：tsc） |
| any | 放弃贴标签的类型，等于放弃体检（能用但别滥用） |

#### 5.1.3 前端框架（以 React 为例）

直接写三件套能做小页面，但界面一复杂就要用**框架（Framework）**——别人搭好的半成品骨架。主流三大家：**React**、**Vue**、**Angular**（React 使用者最多）。

以 React 为例的核心名词：

| 名词 | 人话 |
|---|---|
| 组件 Component | 界面的"积木块"：一个按钮、一张卡片、一个弹窗各是一个组件，像乐高一样拼出页面 |
| 状态 State | 组件"记着的当下情况"：开关是开是关、列表里有几条 |
| 属性 Props | 组件之间的"参数传递"：把标题文字传进卡片组件 |
| 钩子 Hook | 组件能力的"外挂接口"（useState 管状态、useEffect 管时机） |
| JSX | 在 JS 里直接写界面标签的语法（HTML 和 JS 混写） |
| 路由 Router | 管"用户点哪里跳到哪个页面"的导航系统 |
| 虚拟 DOM | React 的提速技巧：先在内存里算好改哪，再一次性改真实界面 |

#### 5.1.4 包管理器与依赖

| 名词 | 人话 |
|---|---|
| 依赖 Dependency | 项目"借用"的别人写好的库（如日期处理库），自己不用重写 |
| 包 Package | 一个可安装的库的最小单位 |
| npm / pnpm / yarn | 三个包管理器（"借书系统"）：帮你下载、安装、管理依赖 |
| package.json | 项目的"身份证+借书单"：记录项目叫什么、借了哪些库、有哪些命令 |
| node_modules | 借来的库堆放的文件夹（很庞大，一般不上传代码库） |
| lockfile（package-lock.json） | "借书清单锁定版"：保证所有人装的版本一模一样 |
| 依赖漏洞 | 借来的库自带安全洞，需要定期检查更新（见第 10 章） |

#### 5.1.5 构建工具

浏览器/桌面壳只认"加工好的成品"，而开发者写的是"原料"。中间的加工厂叫**构建工具（Build Tool）**：**Vite**（新一代，快）和 **Webpack**（老牌）是主流。

| 名词 | 人话 |
|---|---|
| 开发服务器 Dev Server | 构建工具自带的本地预览服务（改代码立刻看效果） |
| 热更新 HMR（Hot Module Replacement） | 改一行代码，界面**不刷新**就地更新（改哪里变哪里） |
| 打包 Bundle | 把成百上千个源文件加工成几个成品文件 |
| 压缩 Minify | 去掉空格注释、缩短变量名，成品文件变小变快 |
| 构建产物 Build Output | 加工好的成品文件夹（dist/ 或 out/），交付给打包环节 |

### 5.2 后端开发

**后端（Backend）** = 用户看不见的部分：逻辑、数据、接口。前端问后端要数据，后端算好给前端。

| 名词 | 人话 |
|---|---|
| 后端语言 Java | 老牌企业级：银行/大厂服务器主力，Android 也用。稳但啰嗦 |
| 后端语言 Python | 解释型"万能胶"：代码像白话，脚本/爬虫/AI/自动化首选，新手第一语言 |
| 后端语言 Go | 编译型，Google 出品：写法简单、跑得快，天生适合服务器和工具 |
| 后端语言 Node.js | 严格说是"运行环境"：让 JS 脱离浏览器跑在服务器上，一门语言前后端通吃 |
| 后端语言 PHP | 最早的"做网站专用"语言，WordPress 等大量老网站用它 |
| 后端语言 Ruby | "让程序员开心"的语言，配 Rails 做出过一代明星网站，现在小众 |
| 后端框架 | Spring（Java）、Django/Flask（Python）、Express（Node.js）——框架帮你处理收请求、发响应这些杂活 |
| 业务逻辑 Business Logic | 产品规则的代码化："满 100 减 20"、"库存不足不能下单" |
| 中间件 Middleware | 请求进来后先过安检（登录校验、日志记录），再进业务 |
| ORM | 把数据库的表格包装成代码里的对象，写代码不用手拼数据库语言 |
| Cookie | 网站存在你浏览器里的"小纸条"（记住你是谁、你的偏好） |
| Session 会话 | 服务器端记着的"你这次访问的状态"（登录状态就靠它） |
| 消息队列 Message Queue | 任务排队的"中转站"（RabbitMQ/Kafka）：下单后发短信这类慢活先排队，前台先返回 |
| WebSocket | 长连接的实时通信：服务器有新消息**主动推**给页面（聊天、实时刷新都靠它） |

> **注意**：不是所有产品都需要后端。**单机工具**（不联网、数据存本机）可以把"后端"浓缩在应用内部，不需要服务器。判断标准只有一个：**数据要不要跨设备共享**。要共享 → 必须有后端服务器；不用共享 → 可以没有。

### 5.3 桌面应用开发专项

桌面应用（双击图标打开窗口的那种）除了前端那套，还有一套自己的名词。主流技术分两派：**Electron**（用网页技术做桌面应用）和 **Tauri**（网页界面+更轻的壳）。

#### 5.3.1 Electron 的核心机制

| 名词 | 人话 |
|---|---|
| Chromium | Google 开源的浏览器内核。Electron 把整个浏览器内核打包进应用——所以界面和网页一样好写，代价是包大 |
| Node.js | 让 JS 脱离浏览器、能操作电脑（读写文件、跑命令）的运行环境 |
| 主进程 Main Process | "总管进程"：和操作系统打交道（弹窗口、读文件、启动外部程序），一个应用只有一个 |
| 渲染进程 Renderer Process | "界面进程"：画界面、响应点击，每个窗口一个 |
| Preload 预加载脚本 | 渲染进程和主进程之间的"安全门岗"，只放行允许的传话 |
| IPC（Inter-Process Communication） | 进程间通信，两个进程之间的"对讲机" |
| BrowserWindow 浏览器窗口 | Electron 里窗口的对象叫法 |

**为什么分两个进程？** 界面进程（渲染进程）随便折腾，哪怕卡死，总管进程（主进程）照常干活、其他窗口不受影响；反过来，总管进程一旦崩溃，整个应用会退出——所以总管进程要尽量简单、少出问题。这是桌面应用稳定性的基石。

#### 5.3.2 打包与分发

| 名词 | 人话 |
|---|---|
| 打包 Packaging | 把代码+内核+图标做成安装包 |
| electron-builder | Electron 生态最流行的打包工具，一条命令出全平台安装包 |
| dmg | macOS 的安装包格式（双击那个磁盘图标） |
| exe / NSIS 安装器 | Windows 的安装包格式 |
| AppImage | Linux 的绿色包格式 |
| 绿色版/便携版 Portable | 不用安装、解压即用的版本 |

#### 5.3.3 签名与公证（macOS 专属痛点）

| 名词 | 人话 |
|---|---|
| 代码签名 Codesigning | 给应用盖"生产厂商章"，证明没被篡改 |
| 公证 Notarization | 苹果官方检查一遍后放行——没公证的应用，用户双击会弹"无法验证开发者，无法打开" |
| 开发者证书 Developer Certificate | 签名要用的"章"，个人开发者账号 99 美元/年 |
| Gatekeeper | macOS 的"门卫"系统，只放行签名过的应用 |
| SmartScreen | Windows 的同类门卫 |
| 自签名 Self-signed | 自己给自己刻章（没花钱的章）——门卫仍会警告，但可右键强制打开 |

**个人开源项目的务实做法**：免费阶段用自签名/不签名分发，在说明文档里写清"如何打开"；有条件（99 美元/年）再正式签名公证。

#### 5.3.4 桌面应用特有的系统能力

| 名词 | 人话 |
|---|---|
| 托盘 Tray | 菜单栏/任务栏右下角的小图标，应用可常驻后台 |
| 开机自启 Auto-launch | 登录系统后自动启动。macOS 用 launchd（LaunchAgent 配置），Windows 用注册表/任务计划 |
| 自动更新 Auto Update | 应用自己检测新版本并更新（Electron 用 electron-updater），更新包通常托管在 GitHub Releases 或自建服务器 |
| 全局快捷键 Global Shortcut | 在系统任何地方按组合键唤起应用 |
| 应用内快捷键 Accelerator | 应用内部的快捷键（⌘S 保存、⌘F 搜索），和全局快捷键是两套体系 |
| 通知 Notification | 系统通知中心弹消息 |
| Dock 程序坞 | macOS 底部图标栏：图标常驻、右键弹出快捷菜单、跳动提醒 |
| 菜单栏应用 Menu Bar App | 只在屏幕顶部菜单栏显示图标的常驻小工具（和托盘 Tray 同族不同形态） |
| 文件关联 File Association | 双击某个后缀的文件自动用你的应用打开（如 .md 关联到编辑器） |
| 自定义 URL 协议 Custom URL Scheme | 注册 `myapp://` 链接，从浏览器/其他应用唤起本应用 |
| Keychain 钥匙串 | macOS 系统级密码保险库，存 Token/密码比明文写配置文件安全 |
| TCC 权限体系 | macOS 的隐私权限管理（摄像头/文件夹访问弹窗就归它管） |
| App Sandbox 沙盒 | macOS 把应用限制在专属区域运行的机制，上 App Store 强制要求 |
| 单例锁 Single Instance Lock | 防止用户开两个实例打架：第二个实例启动时自动唤起第一个 |
| 守护进程 Daemon | 后台常驻、没有界面的服务进程（区别于管多个服务的 pm2） |
| 健康检查 Health Check | 定期自检"还活着吗、端口还通吗"的动作，启动服务后探活也用它 |
| 端口占用/冲突 Port Conflict | 两个程序抢同一个端口号导致启动失败，报错"Address already in use"就是它 |
| 配置文件 Config File | 用户设置存哪：macOS 规范位置是 ~/Library/Application Support/应用名/ |

### 5.4 脚本与命令文件专项（"run 什么命令的文件"）

用户问过的"开发里经常看到 run 什么命令，都是什么文件"——这一节全部讲清。

#### 5.4.1 终端与命令行

| 名词 | 人话 |
|---|---|
| 终端 Terminal | 那个黑框框窗口，用打字的方式指挥电脑 |
| Shell | 终端里解释你命令的"翻译官"：macOS/Linux 用 bash 或 zsh，Windows 用 PowerShell 或 cmd |
| 命令 Command | 你打的一行字："启动服务""复制文件" |
| CLI（Command Line Interface） | 命令行工具的总称（相对 GUI 图形界面而言） |

#### 5.4.2 各种"命令文件"一览

| 文件 | 人话 |
|---|---|
| package.json 的 scripts 段 | JS 项目里定义"常用命令的别名"：`npm run dev` 里的 dev 就是在这里定义的。一条别名背后可以是一长串命令 |
| Shell 脚本 .sh | 一连串命令写成的"批处理剧本"（macOS/Linux），双击/执行即按剧本跑 |
| 批处理 .bat | Windows 版的脚本剧本 |
| Makefile | 老牌命令别名文件（C 生态常用） |
| .env 文件 | 存"环境变量"的隐藏文件：密码、密钥、配置项（数据库地址等），不上传代码库 |
| 环境变量 Environment Variable | 系统级的"全局配置开关"，程序启动时读取 |
| PATH | 特殊环境变量：系统去哪找可执行程序（装新工具就是把它加进 PATH） |
| CI 配置文件（.github/workflows/*.yml） | 告诉 GitHub"代码一提交就自动帮我跑哪些命令"（详见第 7 章） |

**常见命令速查**（JS 生态）：
- `npm install` / `pnpm install` —— 按 package.json 借书（装依赖）
- `npm run dev` —— 跑开发模式（起本地预览服务）
- `npm run build` —— 跑构建（出成品）
- `npm run test` —— 跑测试
- `npm run dist` —— 打包安装包

### 5.5 Git 版本管理

**Git** 是"代码世界的时光机 + 多线协作器"。**GitHub 是一个托管 Git 仓库的网站**——Git 是工具，GitHub 是放代码的网站（两者常被混为一谈）。

| 名词 | 人话 |
|---|---|
| 仓库 Repository（repo） | 一个项目的"档案库"，存所有代码和全部历史版本 |
| 本地仓库 / 远程仓库 | 自己电脑上的档案库 / GitHub 上的档案库 |
| 克隆 Clone | 把远程仓库复制一份到本地 |
| Fork | 把别人的仓库复制成自己的（开源协作第一步） |
| 提交 Commit | 一次"存档"：当前改动打包成一个版本，附一句说明 |
| 暂存区 Staging | 选好"这次存档要包含哪些改动"的篮子 |
| 分支 Branch | 一条独立的开发线（主干旁开岔道），互不干扰 |
| 主分支 main / master | 主干道，放稳定代码 |
| 功能分支 Feature Branch | 每个功能开一条岔道，做完合回主干 |
| 合并 Merge | 把岔道并回主干 |
| 冲突 Conflict | 两条线改了同一个地方，合并时"打架"，需要人工裁决 |
| 拉取请求 PR（Pull Request） | "我这条岔道做完了，请审阅后合并进主干"的正式申请 |
| 代码审查 Code Review | 合并前同事逐行审代码，挑毛病（规范、逻辑、隐患） |
| 推送 Push / 拉取 Pull | 本地仓库和远程仓库之间的同步动作 |
| .gitignore | 声明"哪些文件不进档案库"（如 node_modules、.env） |
| Tag 标签 | 给某个存档起名（如 v1.0.0），发布版常用 |
| Release | GitHub 上的"正式发布"，可附安装包下载 |

**提交信息规范（Conventional Commits）**——存档说明有标准格式：
- `feat: 添加项目登记功能`（新功能）
- `fix: 修复开机自启失效`（修 bug）
- `docs: 更新使用说明`（文档）
- `chore: 升级依赖`（杂务）

**版本号语义化（SemVer）**——`1.2.3` 三位数字各司其职：
- 第 1 位（主版本 Major）：大改版，不兼容旧版（1.0 → 2.0）
- 第 2 位（次版本 Minor）：加了新功能，仍兼容（1.1 → 1.2）
- 第 3 位（补丁 Patch）：只修 bug（1.2.2 → 1.2.3）

### 5.6 代码质量

| 名词 | 人话 |
|---|---|
| ESLint | 代码规范检查器：写得不规范（少分号、声明了没用）当场标黄标红 |
| Prettier | 代码格式化器：一键把代码排版得整整齐齐 |
| Lint（统称） | "查规范"这件事：代码没 bug 但丑/乱/有隐患，lint 来管 |
| 静态检查 Static Analysis | 不运行代码，靠"读代码"找出问题（类型检查属于其中） |
| 代码规范 Style Guide | 团队约定的写法规则（缩进几个空格、变量怎么命名） |
| 注释 Comment | 代码里写给人类看的说明文字 |
| 命名规范 Naming Convention | 变量函数怎么起名（如小驼峰 camelCase） |
| 技术债 Technical Debt | "为了赶工写得糙，以后要还的账"——欠债要记账，不能装看不见 |

**正规团队的代码质量铁律**：lint 不过不让合并；没有 Code Review 不让合并；测试挂了不让合并。

### 5.7 开发阶段的协作铁律

1. **每天提交**：小步快跑，改一点存一点，坏了随时回到上一个存档
2. **一条分支一个功能**：互不干扰，坏了不影响主干
3. **提交信息写清楚**：三个月后自己都看得懂"这次改了什么"
4. **先写测试再写功能**（可选进阶）：用测试定义"什么是做对了"，写完代码测试通过即完成

### 5.8 常见误区

- ❌ **"我代码能跑就是好代码"**——能跑 ≠ 可维护。三个月后看不懂自己的代码 = 没有维护性。
- ❌ **什么都自己写，不借用依赖**——重复造轮子是最大的浪费；但依赖太多也是风险（见第 10 章漏洞扫描）。
- ❌ **不提交、不存档**——代码没进 Git 仓库就等于裸奔，硬盘一坏全完。
- ❌ **提交信息写"更新""改了一点"**——这种存档说明三个月后毫无用处。

### 5.9 开发者的日常工具与工作方式

写代码的日常"装备"和"招式"：

| 名词 | 人话 |
|---|---|
| IDE 集成开发环境 | 写代码的"高级工作台"：编辑器+查错+调试+运行一体化。**VS Code** 是当下最流行的（免费、插件海量） |
| 编辑器 Editor | 纯写代码的软件（IDE 的简化版） |
| 调试 Debug | 找 bug 的过程："程序在哪一步坏了、为什么坏" |
| 断点 Breakpoint | 调试时在代码某一行"设卡"，程序跑到这里暂停，让你检查现场 |
| 日志调试 | 在代码里打 `console.log`（打印一行状态到控制台），看程序走到哪、值是什么——最朴素的调试法 |
| 控制台 Console | IDE 里显示日志输出的面板 |
| nvm / fnm | Node.js 版本管理器：一台电脑装多个 Node 版本，按项目切换（不同项目依赖不同版本） |
| 联调 Joint Debug | 前后端把两边接上一起调试："你调接口我调页面，边连边修" |

**一个 bug 的标准排查流程**：复现问题 → 看日志/控制台输出 → 在可疑处打断点 → 逐步运行观察变量 → 定位出错行 → 修复 → 跑测试确认。

## 第 6 章：测试阶段（QA 的世界）

### 6.1 是什么

测试阶段回答一个问题：**"这东西到底对不对？"**

外行以为测试是"开发完了点一点"，正规团队的测试从写代码第一天就开始了，而且是**分层的**——这就是著名的**测试金字塔（Testing Pyramid）**：

```
         /\        UI 测试（少而精）：模拟真人点界面走全流程
        /  \       端到端测试 E2E：全链路串起来测
       /----\      集成测试：模块之间拼起来测
      /------\     单元测试（最多）：单个零件单独测
```

| 层级 | 名词 | 人话 | 谁写 |
|---|---|---|---|
| 底层 | 单元测试 Unit Test | 测单个零件：这个函数输入 2+2 必须返回 4 | 程序员 |
| 中层 | 集成测试 Integration Test | 零件拼起来测：登录模块和数据库模块配合对不对 | 程序员 |
| 高层 | 端到端测试 E2E（End-to-End） | 模拟真人完整走一遍："注册→登录→下单→付款" | 自动化脚本 |
| 顶层 | UI 测试 | 模拟点击界面元素（自动点按钮填表单） | 自动化脚本 |

### 6.2 标准做法：测试的配套名词

| 名词 | 人话 |
|---|---|
| 测试用例 Test Case | 一条"输入什么 → 期望什么"的检查项（如"输入空用户名→提示不能为空"） |
| 断言 Assertion | 测试里的判定句："结果必须等于 4，否则算失败" |
| 覆盖率 Coverage | 代码有多少比例被测试跑过（80% 是常见及格线） |
| 回归测试 Regression Test | 改完代码后，把老测试全部重跑一遍，确认没改坏旧功能 |
| 冒烟测试 Smoke Test | 上线前快速点一遍核心流程，"能不能开机的检查" |
| 手动测试 / 自动化测试 | 人肉点 vs 脚本自动跑；能自动化的优先自动化 |
| 测试环境 Staging | 假的生产环境，上线前先在这里全量演练 |
| 生产环境 Production | 用户真正用的环境，神圣不可轻易动 |
| Bug / 缺陷 | 产品的毛病；Bug 有完整生命周期：**报告→复现→修复→验证→关闭** |
| 验收测试 UAT（User Acceptance Testing） | 最后一步：**让真实用户（或产品方）亲手验收**，说行才上线 |

### 6.3 常见误区

- ❌ **"开发自测过就行"**——写代码的人自带盲区，自己永远测不出自己的错。
- ❌ **只测正常情况**——真正的 bug 都在边界：空输入、超大文件、断网瞬间、快速连点。
- ❌ **修一个 bug 不跑回归测试**——按下一个葫芦浮起一个瓢是常态。
- ❌ **UAT 走形式**——产品方不亲手用就点头，上线后全是你自己买单。

### 6.4 测试的常用辅助手段

| 名词 | 人话 |
|---|---|
| Mock 假数据 | 测试时用"假的后端/假的数据"顶替真家伙——真接口没写好也能先测前端 |
| 压测（性能测试）Load Testing | 模拟大量用户同时使用，看系统扛不扛得住（如"1 万人同时下单"） |
| 性能剖析 Profiling | 用工具测量程序每一段花了多少时间，找出最慢的那段 |

## 第 7 章：运维阶段（DevOps 的世界）

### 7.1 是什么

运维回答一个问题：**"怎么让它 7×24 小时稳稳跑在线上？"**

> ⚠️ 先说明：**只有需要联网共享数据的服务型产品才有这个阶段**。单机工具（数据都在用户本机）没有服务器可运维——这是单机工具的重大红利。但本章内容值得懂，因为"日志""监控"的概念单机工具也用得上。

### 7.2 标准做法：服务器与部署

| 名词 | 人话 |
|---|---|
| 服务器 Server | 租来的"云端电脑"，24 小时开机，你的程序跑在上面 |
| 云服务商 Cloud Provider | 出租云端电脑的公司：AWS（亚马逊）、阿里云、腾讯云、Google Cloud |
| VPS（Virtual Private Server） | 一台虚拟的独立服务器（便宜入门款） |
| 部署 Deploy | 把代码"运"到服务器上跑起来的过程 |
| Nginx | 最流行的服务器软件：接待访客请求的"前台" |
| Docker | 把程序+环境打包成"集装箱"，到任何服务器都能原样跑 |
| 容器 Container | Docker 打包出的集装箱 |
| K8s（Kubernetes） | 管理成千上万集装箱的调度系统（大厂才需要） |
| 负载均衡 Load Balancer | 访客太多时，把请求分给多台服务器的"分流交警" |
| 反向代理 Reverse Proxy | Nginx 的核心工作：访客找"前台"，前台把请求转给后台的服务——对外只露一个门 |
| CDN | 内容分发网络：把图片、静态文件缓存到全球各地的节点，用户就近取——加载更快 |
| 进程守护 Process Supervisor | "看门人"（pm2/systemd）：服务挂了自动拉起、开机自动启动 |
| 扩容 Scale | 不够用了加服务器（扩容/缩容） |
| 灾备 Disaster Recovery | 灾难预案：机房炸了/数据删错了，怎么快速恢复（异地备份+恢复演练） |

### 7.3 标准做法：域名与证书

| 名词 | 人话 |
|---|---|
| IP 地址 | 服务器的门牌号（如 192.168.1.1） |
| 域名 Domain | 给门牌号起的好记名字（如 example.com） |
| DNS | "域名→门牌号"的全球电话簿 |
| HTTP / HTTPS | 网页传输协议；HTTPS 多一层加密，浏览器地址栏的锁图标 |
| SSL/TLS 证书 | HTTPS 加密要用的"数字锁"，从证书机构申请（有免费版 Let's Encrypt） |
| ICP 备案 | 中国特有：用国内服务器对外提供服务必须先备案（免费但流程要几周）；用海外服务器或纯 GitHub 托管则不需要 |

### 7.4 标准做法：日志体系（用户点名专项）

**日志（Log）** = 程序的"行车记录仪"：程序每干一件事，就往日志文件里写一行。用户报 bug 时，工程师第一件事就是看日志——**没有日志的 bug 是悬案**。

| 名词 | 人话 |
|---|---|
| 应用日志 | 程序自己写的记录（"用户张三登录成功"） |
| 访问日志 | 谁在什么时候访问了哪个页面 |
| 错误日志 | 出错时的现场记录（错在哪一行、什么原因） |
| 日志分级 Log Level | 记录分轻重：**DEBUG**（调试细节）/ **INFO**（正常流水）/ **WARN**（警告，可能要出事）/ **ERROR**（出错了） |
| 日志轮转 Rotation | 日志文件会越来越大，按天/按大小切割归档，旧的定期删 |
| 日志保留期 Retention | 日志留多久（如 7 天） |

### 7.5 标准做法：监控与告警

| 名词 | 人话 |
|---|---|
| 监控 Monitoring | 实时盯服务健康（响应快不快、内存够不够），用图表展示 |
| 告警 Alert | 出问题自动通知人（短信/电话/飞书机器人） |
| 崩溃收集 Crash Reporting | 应用闪退时自动把"案发现场"上报给收集平台 |
| Sentry | 最流行的崩溃收集服务（开源、有免费额度） |
| 可用性 SLA | "保证 99.9% 时间可用"的服务承诺（大厂标准 99.99%） |

### 7.6 标准做法：CI/CD 自动化流水线（用户点名专项）

**CI/CD** = 把"测试→构建→部署"这些重复劳动交给机器人自动干。

| 名词 | 人话 |
|---|---|
| CI（Continuous Integration）持续集成 | 代码一提交，机器人自动跑测试——早发现早治疗 |
| CD（Continuous Delivery/Deployment）持续交付/部署 | 测试通过后，机器人自动打包甚至自动上线 |
| GitHub Actions | GitHub 自带的机器人平台：在 `.github/workflows/*.yml` 里写"提交后帮我跑这些命令" |
| 流水线 Pipeline | 一串自动化步骤的总称（提交→装依赖→测试→打包） |
| 自动打包 | CI 机器人在云端自动跑 `npm run build`、`npm run dist`，产出安装包 |

**CI/CD 对开源项目的价值**：每次提交自动测试、自动出安装包，人不用管——这正是第 5.4 节说的"CI 配置文件"的用处。

### 7.7 常见误区

- ❌ **不记日志**——出了 bug 只能靠猜。至少记：启动、关键操作、出错现场。
- ❌ **日志里存密码**——日志可能被泄露，敏感信息要脱敏。
- ❌ **小项目全套上 Docker + K8s**——杀鸡用核弹，运维复杂度吃光开发时间。

## 第 8 章：发布阶段

### 8.1 是什么

发布回答一个问题：**"怎么把成品送到用户手里？"**

### 8.2 标准做法

| 名词 | 人话 |
|---|---|
| 打包 Build | 把源码加工成可安装/可运行成品 |
| 发布 Release | 成品正式对外提供下载/更新 |
| 分发渠道 Distribution Channel | 送到用户手里的路径：**应用商店**（App Store 等，要审核）/ **官网下载** / **GitHub Releases**（开源项目标准渠道） |
| 灰度发布 Gray Release | 先放给 1% 用户试，没问题再全量——"小范围试水再放开" |
| 回滚 Rollback | 新版出大问题，一键退回上一个版本 |
| A/B 测试 | 同一功能做两个版本，随机分给两组用户，看数据定胜负 |
| Changelog 更新日志 | "这一版改了什么"的说明文档 |
| 版本冻结 Freeze | 发布前几天禁止乱改代码，保证发的是测过的那个版本 |
| 热修复 Hotfix | 上线后发现紧急 bug，跳过常规流程火速发一个小补丁版 |

### 8.3 开源项目的发布标准姿势

1. 代码推上 GitHub（main 分支稳定）
2. 打 Tag（v1.0.0）
3. 创建 Release：写更新说明 + 上传安装包（dmg/exe）
4. 用户从 Release 页下载安装

### 8.4 常见误区

- ❌ **发布前不冒烟测试**——把"点两下就崩"的版本发出去，口碑一次清零。
- ❌ **Changelog 写"修复若干问题"**——等于没说。写清楚"新增什么、修复什么"。
- ❌ **不做回滚预案**——上线前先想好"万一崩了怎么退"。

## 第 9 章：运营与迭代阶段

### 9.1 是什么

发布之后才是真正的开始：**收集反馈 → 排优先级 → 做下一版 → 再发布**，循环往复（回到第 1 章流程图的最底部箭头）。

### 9.2 标准做法

| 名词 | 人话 |
|---|---|
| 数据埋点 Analytics | 在代码里埋"计数点"，统计用户点了哪个按钮、停留多久（开源自托管方案：Umami/Plausible；商业方案：Google Analytics） |
| 用户反馈渠道 | Issue 区、评论区、客服群——产品改进的第一手情报 |
| 迭代节奏 Iteration Cadence | 多久发一版（大厂双周，个人项目按需） |
| Roadmap 路线图 | 未来几个月计划做什么的公开地图 |
| 用户留存 Retention | 用户用了还会不会回来（产品的生死指标） |

### 9.3 开源治理专项

开源项目有一套社区规范：

| 名词 | 人话 |
|---|---|
| License 开源协议 | 规定"别人能用你的代码干什么"的法律文本。三大件：**MIT**（最宽松：随便用，保留署名即可）、**Apache 2.0**（宽松+专利保护）、**GPL**（严格：用了你的代码，他的代码也必须开源） |
| README | 仓库首页的说明书：项目是什么、怎么装、怎么用（开源项目的门面） |
| Contributing 指南 | 告诉想参与的人"怎么贡献代码"（怎么提 Issue、怎么提 PR） |
| Issue 模板 / PR 模板 | 提前写好的提问格式，让反馈规范可读 |
| Star / Fork / Watch | GitHub 三连：收藏 / 复制到自己名下 / 订阅动态（开源项目的"人气值"） |
| Code of Conduct | 社区行为守则 |

### 9.4 常见误区

- ❌ **发布完就撒手**——开源项目的价值一半在产品、一半在持续维护的信任感。
- ❌ **License 不选或乱选**——不选 License 默认"保留所有权利"，别人想用都不敢用。
- ❌ **README 只有两行字**——路人 30 秒看不懂这项目是干嘛的，就走了。

## 第 10 章：安全专项

### 10.1 是什么

安全回答一个问题：**"这东西会被怎么攻破、怎么防？"**

### 10.2 核心概念（人话版）

| 名词 | 人话 |
|---|---|
| 加密 Encryption | 把内容搅乱成只有拿钥匙的人能看懂 |
| 哈希 Hash | 单向"指纹计算"：同一个东西算出的指纹永远一样，但指纹推不回原物（存密码用哈希，不用明文） |
| 密钥 Key / Secret | 密码/凭证的总称（数据库密码、API 密钥） |
| Token 令牌 | 登录后发的"通行证"，带着它才证明你登录过 |
| HTTPS | 传输加密的网页协议，防偷听篡改 |
| XSS（跨站脚本攻击） | 坏人往你的页面里塞假代码，偷访客信息 |
| SQL 注入 | 坏人往输入框里塞数据库命令，偷整张表 |
| 最小权限原则 | 程序只申请它必须有的权限，多一个都是风险 |
| 依赖漏洞扫描 | 检查借来的库有没有已知安全洞（npm 生态命令：`npm audit`） |
| 供应链攻击 | 坏人攻破某个依赖库，间接感染所有用它的人（所以依赖要少、要审查） |
| 脱敏 Desensitization | 日志/截图里把手机号、密码打码 |
| OAuth | 第三方登录的标准协议："用微信登录本站"——本站不碰你的密码，只拿通行证 |
| 2FA（双因素认证） | 登录要过两道关：密码 + 短信/动态码，防密码泄露后被冒用 |
| RBAC（基于角色的权限管理） | 多人系统里按角色发权限：管理员能删、编辑能改、访客只能看 |
| 渗透测试 Penetration Test | 请安全专家像黑客一样攻击自己的系统，找出漏洞 |

### 10.3 桌面应用的安全要点

| 要点 | 人话 |
|---|---|
| 签名防篡改 | 有签名的应用被改过就露馅，用户知道它"原装" |
| 权限申请克制 | macOS 会在应用访问敏感位置时弹窗询问（TCC 权限体系），设计上尽量少碰 |
| 不联网就不泄露 | 单机工具最大的安全优势：数据不出本机，攻击面天然小 |
| 更新通道安全 | 自动更新必须走 HTTPS，防止更新包被调包 |

### 10.4 常见误区

- ❌ **"我的小项目没人攻击"**——依赖漏洞和供应链攻击专挑小项目下手（因为没人管）。
- ❌ **密钥写进代码里提交**——代码一旦公开（开源），密钥等于全世界可见。
- ❌ **收集用不到的数据**——多存一份用户数据就多一份责任。

### 10.5 数据合规（产品的法律底线）

| 名词 | 人话 |
|---|---|
| 个保法（PIPL） | 中国《个人信息保护法》：收集用户信息要告知、要同意、要能删除 |
| GDPR | 欧盟通用数据保护条例：全球最严的数据法规（服务欧洲用户就要遵守） |
| 隐私政策 Privacy Policy | 告诉用户"我收集什么、拿来干什么"的声明文档——收集数据的产品必备 |
| 用户协议 ToS（Terms of Service） | 使用规则和服务条款 |

**给个人项目的底线**：能不收集就不收集；收集了就要有隐私政策；用户要求删除就必须能删。

## 第 11 章：性能专项

### 11.1 是什么

性能回答一个问题：**"用起来快不快、顺不顺、省不省？"**

### 11.2 性能指标（人话版）

| 指标 | 人话 |
|---|---|
| 启动时间 Launch Time | 双击图标到窗口出现，几秒算及格（桌面应用 3 秒内良好） |
| 响应时间 Response Time | 点一下到有反应的时间（100ms 内感觉"瞬间"） |
| 内存占用 Memory Usage | 吃多少内存（占用过高会拖慢整台电脑） |
| CPU 占用 | 吃多少算力（后台空转还吃 CPU 就是有毛病） |
| FPS 帧率 | 动画每秒画几帧（60 帧顺滑，低于 30 帧感觉卡） |
| 卡顿 Jank | 界面一顿一顿的现象 |

### 11.3 优化手段（人话版）

| 手段 | 人话 |
|---|---|
| 缓存 Cache | 常用东西提前放抽屉，省得每次现找 |
| 异步 Async | 慢活放后台干，界面照常响应（快递在途，你继续干别的） |
| 懒加载 Lazy Loading | 用到再加载，不提前扛所有东西 |
| 压缩 Compression | 文件瘦身，传得快占得少 |
| 批处理 Batching | 十个请求合并成一次发，省十次来回 |

### 11.4 常见误区

- ❌ **提前优化**——"我猜这里慢，先优化了再说"。铁律：先测量出真的慢，再优化慢的地方。
- ❌ **用卡顿换功能**——功能再多，用起来难受就全白搭。
- ❌ **只在顶级电脑上测试**——用户的电脑一般没你的好。

## 第 12 章：兼容性与国际化专项

### 12.1 兼容性

| 名词 | 人话 |
|---|---|
| 系统版本兼容矩阵 | "支持 macOS 12 及以上、Windows 10 及以上"这类明确声明，测试时每个版本都要验 |
| 跨平台 Cross-platform | 一套代码跑多个系统（Mac/Win/Linux），跨平台框架的卖点 |
| 原生 Native | 用系统官方语言单独为每个平台写——体验最好，成本翻倍 |

### 12.2 国际化与本地化

| 名词 | 人话 |
|---|---|
| 国际化 i18n（internationalization） | 开发时就做好"能换语言"的结构（所有文案集中管理，不写死在代码里） |
| 本地化 l10n（localization） | 针对具体语言做翻译和适配（中文版、英文版） |
| 可访问性 a11y（accessibility） | 残障用户也能用：屏幕朗读（VoiceOver）、大字体、键盘操作 |

### 12.3 常见误区

- ❌ **文案写死在代码里**——以后想加英文版，要从代码海里捞字，工程浩大。
- ❌ **只测最新系统**——用户里总有人用老版本。
- ❌ **忽略键盘党**——全程只能鼠标操作，对很多人等于不能用。

## 第 13 章：数据专项

### 13.1 是什么

数据专项回答：**"数据存在哪、怎么保命、怎么搬家？"**

### 13.2 存储方案全家桶（从轻到重）

| 方案 | 人话 | 适合 |
|---|---|---|
| 纯文件（JSON/CSV/YAML） | 直接存成文本文件，人眼能读、复制即备份 | 数据量小、结构简单的项目（几十上百条记录） |
| SQLite | 装在程序里的微型数据库（一个文件），不需要装服务器 | 单机应用、手机 app 的标配 |
| MySQL / PostgreSQL | 专业的服务器级关系型数据库 | 联网服务型产品的标配 |
| Redis | 内存里的极速数据库 | 存缓存、排行榜等高频数据 |
| 对象存储 OSS（AWS S3/阿里云 OSS） | 云上的"网盘服务"，存图片视频大文件 | 用户上传的文件 |
| 云数据库 | 云厂商代管的数据库（不用自己运维） | 不想养运维的团队 |

### 13.3 备份与迁移

| 名词 | 人话 |
|---|---|
| 备份 Backup | 定期把数据复制一份存别处——**没有备份的数据不是资产，是风险** |
| 恢复 Restore | 从备份把数据救回来 |
| 导出/导入 Export/Import | 把数据打包成文件带走/搬进来（换电脑、换软件的救命功能） |
| 迁移 Migration | 数据从旧结构搬到新结构（升级版本时改数据格式） |
| 数据一致性 Consistency | 数据前后对得上（付了钱订单却没记录 = 不一致） |

### 13.4 常见误区

- ❌ **数据只在用户本地且没有导出功能**——电脑一坏，用户的数据全没，产品直接背锅。
- ❌ **升级版本改数据格式却不做迁移**——老用户一升级，数据读不出来。
- ❌ **"小数据用数据库"过度设计**——上百条数据用 JSON 文件完全够，杀鸡不用牛刀。

## 第 14 章：专业术语速查表（Glossary）

> 本章是全文档的"字典"：开发中遇到任何不懂的词，来这查。
> 分 8 类，每类内英文词按字母排序在前、中文词按拼音排序在后。正文各章详解过的词这里只留一句话人话。

### A. 基础概念

| 词 | 人话 |
|---|---|
| API | 程序之间约定的传话规则 |
| Bug | 产品的毛病、程序的错误 |
| CLI | 命令行工具（黑框框打字操作） |
| Debug | 调试：找 bug 的过程 |
| GDPR | 欧盟数据保护条例：全球最严数据法规 |
| GUI | 图形界面（点点点操作） |
| IDE | 集成开发环境：写代码的工作台（如 VS Code） |
| JSON | 数据交换的标准文本格式 `{"名": "值"}` |
| Markdown | 用符号排版文字的轻量格式（本文件就是） |
| SDK | 开发工具包：别人打包好的一整套开发工具 |
| RegExp 正则表达式 | 高级查找语法：写一串符号，就能在长文本里批量找到/替换符合规律的内容 |
| UI | 用户界面（看得见的部分） |
| URL | 网址、链接 |
| XML | JSON 之前的老牌数据格式，标签一对对写 |
| YAML | 比 JSON 更"像人话"的配置文件格式，靠缩进分层、不用括号 |
| 编译器 | 把代码翻译成电脑能直接执行的机器码 |
| 程序 | 写好的代码跑起来的样子 |
| 代码 | 写给电脑看、指挥电脑干活的文字 |
| 断点 | 调试时在代码某行"设卡"，暂停检查现场 |
| 端口 | 电脑上的"门牌号"，一个程序占一个端口提供服务 |
| 个保法 | 中国个人信息保护法：收集信息要告知、同意、可删除 |
| 后端 | 用户看不见的部分（逻辑与数据） |
| 架构 | 代码世界的房屋结构图 |
| 解释器 | 解释型语言"边翻译边跑"的执行者。语言分两派：编译型（如 C/Go）先整本翻译成机器码再跑，快但改一次编一次；解释型（如 Python/JS）边翻边跑，灵活但稍慢 |
| 技术选型 | 选择语言、框架、数据库的决策过程 |
| 进程 | 正在运行中的一个程序实例 |
| 开源 | 源代码公开，人人可看可用 |
| 客户端 | 用户这一侧的软件（相对服务器而言） |
| 库 | 别人写好的功能集合，借来用 |
| 框架 | 别人搭好的半成品骨架，往里填内容 |
| 前端 | 用户看得见的部分（界面） |
| 软件 | 程序的正式叫法 |
| 线程 | 进程内部的"人手"，多线程 = 多只手同时干活 |
| 依赖 | 项目借用的别人写的库 |
| 隐私政策 | 说明"收集什么数据、拿来干什么"的声明文档 |
| 运行环境 | 程序跑起来所需的基础设施（如 Node.js 环境） |
| 终端 | 打字指挥电脑的黑框框窗口 |
| 字节 | 存储的最小计量单位（1MB = 约 100 万字节） |

### B. 开发流程

| 词 | 人话 |
|---|---|
| A/B 测试 | 两个版本随机分给两组用户，数据定胜负 |
| Backlog | 需求池：待做功能的排队名单 |
| Beta/RC | 公测版 / 发布候选版 |
| Changelog | 每个版本"改了什么"的说明 |
| CI/CD | 机器人自动跑测试（CI）和自动部署（CD） |
| Code Review | 合并前同事逐行审代码 |
| GDPR | 欧盟数据保护条例：全球最严数据法规 |
| Git | 代码版本管理工具（时光机） |
| GitHub | 托管 Git 仓库的网站（放代码的地方） |
| Hotfix | 热修复：紧急 bug 火速发的补丁版 |
| Issue | GitHub 上的问题反馈单 |
| MVP | 最小可行产品：先做最能解决痛点的功能 |
| P0/P1/P2 | 优先级：必须有 / 应该有 / 可以有 |
| PR | 拉取请求："我的分支做完了，请审阅合并" |
| PRD | 产品需求文档，项目的宪法 |
| Release | GitHub 上的正式发布（可附安装包） |
| Roadmap | 未来版本的路线图 |
| Sprint | 冲刺：敏捷开发的一个工作周期（1-2 周） |
| Tag | 给某个代码存档起的版本名（v1.0.0） |
| 迭代 | 一轮一轮的开发周期 |
| 估时 | 估算任务工时的动作 |
| 灰度发布 | 先放小部分用户试水，再全量 |
| 回滚 | 新版本出问题，退回上一版 |
| 里程碑 | 交付时间节点 |
| 联调 | 前后端把两边接上一起调试 |
| 敏捷开发 | 小步快跑、频繁交付的开发方式 |
| 排期 | 估算任务并排出时间表 |
| 任务拆解 | 把 PRD 功能拆成可执行的小任务 |
| 需求管理工具 | Jira/Trello/Linear 等管需求池和进度的软件 |
| 需求评审 | 开工前全员对齐 PRD 的会议 |
| 验收标准 | "做到什么程度算完"的可验证标准 |
| 用户故事 | "作为____我想____以便____"的需求句式 |

### D. 后端与数据

| 词 | 人话 |
|---|---|
| 2FA | 双因素认证：密码之外再加一道验证 |
| C | 最古老的"元老"语言：操作系统和各类工具的地基，现在主要在底层与嵌入式 |
| C# | 微软系语言：写 Windows 桌面应用（.NET）和 Unity 游戏的主流 |
| C++ | C 的升级版：游戏引擎/大型软件主力，性能天花板但难学，新手知道名字即可 |
| Cookie | 存在浏览器里的小纸条（记住你是谁） |
| Dart | 谷歌出品：写 Flutter 跨平台应用（一套代码跑手机/桌面/网页）的专用语言 |
| Go | 编译型后端语言，Google 出品：写法简单、跑得快，天生适合写服务器和工具 |
| Java | 老牌企业级后端语言，"一次编写到处运行"，银行/大厂服务器主力，也写 Android |
| Kotlin | Android 官方语言（Java 的现代升级版），写安卓应用首选 |
| Lua | 小巧的嵌入脚本语言，游戏 mod、配置脚本常用 |
| MATLAB | 数学家和工程师的计算语言：矩阵运算、科研绘图 |
| MySQL | 最流行的关系型数据库之一 |
| NoSQL | 非关系型数据库总称（灵活松散） |
| OAuth | 第三方登录的标准协议（"用微信登录"） |
| Objective-C | iPhone 最早的官方语言，已被 Swift 取代，老 App 代码还在 |
| ORM | 用写代码的方式操作数据库的翻译层 |
| PHP | 最早的"做网站专用"语言，WordPress 等大量老网站用它，生态仍庞大 |
| PostgreSQL | 功能强大的开源关系型数据库 |
| Python | 解释型"万能胶"语言：代码像念白话一样好懂，写脚本/爬虫/AI/自动化全靠它，新手第一语言 |
| R | 统计学家专用的数据分析语言：做图表、跑统计检验 |
| RBAC | 按角色发权限的权限管理体系 |
| Redis | 内存极速数据库（存缓存用） |
| RESTful | 流行的 API 设计风格 |
| Ruby | 以"让程序员开心"为理念的语言，配 Rails 框架做出过一代明星网站，现在小众 |
| Rust | 注重"绝对安全"的现代系统语言：快得像 C，又能在写代码时拦住内存崩溃，Tauri 和很多新 CLI 工具都用它写 |
| Session | 服务器记着的"本次访问状态"（登录态） |
| SQL | 和数据库对话的查询语言，写法像英文句子：`SELECT 名字 FROM 用户表 WHERE 年龄>30` |
| SQLite | 装进程序里的微型数据库（单文件） |
| Swift | 苹果官方原生语言：只给 iPhone/Mac 写程序时用它，体验最好但出不了苹果家门 |
| Token | 登录后发的通行证 |
| WebSocket | 实时通信长连接（服务器主动推消息） |
| 备份 | 数据复制一份存别处保命 |
| 表 | 数据库里的一张表格 |
| 关系型数据库 | 表与表有严格关联的数据库 |
| 哈希 | 单向指纹计算（存密码用） |
| 缓存 | 常用东西提前放抽屉 |
| 记录 | 表格的一行 |
| 加密 | 内容搅乱，只有拿钥匙的能看懂 |
| 接口 | API 的口语说法 |
| 幂等 | 同一请求发两次结果一样 |
| 密钥 | 密码/凭证的总称 |
| 迁移 | 数据从旧结构搬到新结构 |
| 死锁 | 两件事互相等对方放资源，全卡死 |
| 事务 | 一组操作要么全成功要么全回滚 |
| 索引 | 表格的目录，查询加速 |
| 消息队列 | 任务排队的中转站（RabbitMQ/Kafka） |
| 序列化 | 数据对象↔JSON 文本的互转 |
| 业务逻辑 | 产品规则的代码化 |
| 中间件 | 请求进来先过的安检层 |
| 主键 | 每行数据的身份证号 |
| 状态码 | 结果的数字代号（200 成功/404 找不到/500 挂了） |
| 字段 | 表格的一列 |

## 附录：一句话回顾全文

> 一个产品 = 先想清楚（需求）→ 再画明白（设计）→ 定好怎么搭（技术方案）→ 动手写（开发）→ 验对了（测试）→ 跑稳了（运维）→ 送到手（发布）→ 继续改（运营迭代）。
> 专业名词只是让这一切不产生歧义的"普通话"。每个环节都可以由 AI 代劳，但**"要做什么、好不好用"的产品判断，永远由人来做**。
