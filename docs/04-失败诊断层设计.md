# Reopen 失败诊断层设计（L4：把报错翻成人话）

> 生成日期：2026-09-23。基于 `projectManager.ts` 现有失败路径梳理。

## 一、一句话

现状：兜底时用户看到的是 **`进程提前退出（退出码 1）`**——这是技术黑话，等于没说。
目标：失败时要么给出**一句人话 + 一个能点的按钮**，要么**诚实地说"这个我搞不定，但这是原因，你该去做什么"**。

**核心原则：能自动修的直接修（静默），修不了的翻译成人话，翻译不了的把材料备好让人能拿去问。**

**产品边界（2026-09-23 拍板）：零 AI 接入、零网络依赖——纯本地规则引擎。** 详见 4.4。

## 二、现状代码定位

| 位置 | 关键函数 | 现状行为 |
|---|---|---|
| `projectManager.ts:518` | `hasPermissionDenied()` | 正则匹配日志 `Permission denied` → 补执行位自动重试一次 |
| `projectManager.ts:525` | `hasCrossPlatformDeps()` | 匹配 12 种跨平台特征 → 静默 `npm install --force` 重装 |
| `projectManager.ts:810` | `kill-residue` | 端口被**自己**残留进程占用 → 一键终止重启 |
| `projectManager.ts:457/468` | `npm-install` | 依赖没装 → 一键装依赖 |
| `projectManager.ts:1063` | **兜底** | `failWithLogHint(rt, project, '进程提前退出（退出码 ${code}）')` ← **问题所在** |
| `types.ts:176` | `ProjectFix` | `kind: 'npm-install' \| 'kill-residue'` —— **只有 2 种** |
| `processLogs.ts` | `createProcessLogs()` | stdout/stderr 已全量捕获并回调 → **诊断层所需的原料已经齐了** |

**结论**：架构不用改，原料已经全在手里（stderr 流过 `pipeLog`）。要做的只是**在 `exit` 分支前加一层模式匹配**。

>
> 真正的缺口不是「没有诊断」，而是：① 12 条里只有 2 条带可点按钮，其余 10 条只给文案、让用户自己去终端敲；② 没有归属层；③ 兜底是技术黑话；④ 规则埋在 `projectManager.ts` 里不可单测。实施范围据此收窄（详见第十二节）。

### 3.1 从「分类」升级到「定位」（2026-09-24 补）

上面的表回答的是「**这是哪一类问题**」。但用户真正想知道的是「**卡在哪一个点上**」——修不了没关系，**得让我知道卡在哪**。

**好消息：答案通常已经写在日志里了，只是混在技术黑话中间。** 我们要做的只是把它**抠出来，放进人话里**：

| 场景 | 日志原文 | 抠什么 | 展示成 |
|---|---|---|---|
| 缺配置项 | `Missing required environment variable: DATABASE_URL` | 变量名 | 「缺一个配置项：**DATABASE_URL**」 |
| 缺配置文件 | `ENOENT: no such file, open '/x/.env.local'` | 文件名 | 「缺配置文件 **.env.local**」 |
| 连不上数据库 | `connect ECONNREFUSED 127.0.0.1:5432` | 主机:端口 | 「它想连 **127.0.0.1:5432**（PostgreSQL），本机没有」 |
| 缺文件 | `Cannot find module '/x/src/config.js'` | 路径 | 「它在找 **src/config.js**，这文件不存在」 |
| 语法错误 | `SyntaxError ... at src/app.js:42` | 文件:行号 | 「**src/app.js 第 42 行**有语法错误」 |
| 私有依赖 | `404 ... GET https://npm.corp.com/@c/utils` | 包名 + 源 | 「要从**公司私有源**装 **@c/utils**，你没登录」 |
| 连内网 | `getaddrinfo ENOTFOUND git.corp.internal` | 域名 | 「它要连 **git.corp.internal**（公司内网）」 |

**全部是正则提取，不需要 AI、不需要联网。**

### 3.2 故障卡片：四层结构

定位之后，展示要固定成四层——**每一层回答用户心里的一个问题**：

| 层 | 回答的问题 | 内容 |
|---|---|---|
| 1️⃣ **卡在哪** | 发生了什么？ | 定位到具体对象（**只陈述事实**，不含猜测） |
| 2️⃣ **为什么** | 这是什么意思？ | 一句人话解读 |
| 3️⃣ **谁能修** | 我该找谁？ | **归属**：Reopen / 你 / 项目作者 / 运维 |
| 4️⃣ **下一步** | 我现在干什么？ | 可执行建议 + 「复制日志」 |

**第 3 层「归属」是新东西，对小白用户极重要**——它回答的不是"怎么修"，而是"**这事归谁管**"：

| 归属 | 含义 | 卡片措辞 |
|---|---|---|
| 🟢 `reopen` | 我能修 | 「点这里，我帮你修」 |
| 🟡 `user-env` | 你的电脑缺东西 | 「你需要装个 X（命令给你备好了）」 |
| 🔵 `external` | 项目要的外部资源 | 「这项目要连 X，只有项目作者知道怎么办」 |
| 🔴 `project` | 项目代码有问题 | 「项目代码本身有问题，得改代码」 |

卡片示例：

```
⚠️ 启动失败
────────────────────────────────
它想连 127.0.0.1:5432（PostgreSQL 数据库），
但这台 Mac 上没有跑这个服务。

这需要项目作者告诉你数据库在哪，
或者你自己起一个 —— 命令我备好了。

[复制日志]   [给我 Docker 命令]
```

**注意两个按钮的分工**：右边是能干的事（`run`），左边是干不了时的兜底（复制日志）。**永远给用户留一条路。**

## 四、兜底诊断：三个信号 + 文案改造（**优先级最高**）

### 4.1 先说结论：退出码帮不上忙

现在的兜底是 `进程提前退出（退出码 ${code ?? signal}）`。**退出码回答的是"有没有出错"，不是"错在哪"**：

| 退出码 | 含义 | 诊断价值 |
|---|---|---|
| **1** | 通用错误，**绝大多数程序的默认值** | 几乎为零 |
| **7** | **curl**：连不上主机。别的程序可能是别的意思 | 低（要先知道是谁退的） |
| 126 | shell 标准：命令不可执行（权限） | 高 |
| 127 | shell 标准：命令未找到 | 高 |
| 130 / 137 / 143 | 被信号中断（Ctrl+C / kill -9 / SIGTERM） | 中 |
| 35 | **curl**：SSL 连接失败（**代理问题的经典信号**） | 高 |

**关键**：退出码**不是标准化的**——除了 shell 那 4 个（126/127/130/137），其余数字的含义由**程序自己定义**。所以单看「退出码 7」没有意义，必须结合「**是谁退的 + 日志写了什么**」。

> 你早就在自己的项目里做过这件事：lanzhuo-imageee 的 `curl exit 35` → 诊断出是代理问题 → `LANZHUO_PROXY_DIRECT=1` 解决。
> **这正是 Reopen 要对用户做的事**——退出码本身没用，**"退出码 + 上下文 → 一句人话"**才有用。

### 4.2 ⭐ 存活时长：被忽略的高价值信号

代码里已经记了 `startedAt`，但**没用"启动了多久才退"来做诊断**。这个信号很便宜，而且很准：

| 存活时长 | 含义 | 高概率原因 |
|---|---|---|
| **< 0.8s** | 命令**根本没跑起来** | D1 命令不存在 / D14 脚本不存在 / D16 语法错误 |
| **0.8~8s** | 跑起来了，**初始化就挂** | D5 依赖没装 / D12 端口占用 / D17 缺配置 |
| **8~30s** | 跑到某一步失败 | D20 连不上数据库 / 网络超时 |
| **≈30s** | **健康检查超时**（进程可能还活着） | 端口没监听 / 绑错地址 |

> ⚠️ **2026-09-24 修正**：分桶阈值从 500ms / 5s 放宽到 **800ms / 8s**。因为项目用 `shell: true` 起进程，测到的是「shell 退出」而不是「node 崩溃」，中间夹着 200~2000ms 的固定开销。而且这个信号**只做并列提示、不当主判据**（见第十二节）。

配合日志一起判断，准确率明显高于只看日志。建议在 `ProjectStatusEvent` 里加 `durationMs`。

### 4.3 文案三板斧

1. **一句人话**：「项目启动后 0.3 秒就退出了」
2. **可能有用的猜测**（命中 D 表就展示，没命中则跳过）
3. **一键复制完整日志** ← ⚠️ **纯剪贴板操作，零网络、零 AI**（见 4.4）

### 4.4 产品边界：不接入任何 AI（2026-09-23 拍板）

**「复制日志」按钮只是把文本写进系统剪贴板。** 用户想拿它去问谁是用户的自由——Reopen **不发起网络请求、不调用模型、不接入 agent bridge**。

这不只是妥协，是**正确的产品选择**：

| 理由 | 说明 |
|---|---|
| 离线可用 | 用户的项目可能在内网，诊断不能依赖外网 |
| 隐私 | 日志里可能有密钥、内网地址、客户数据 |
| 确定性 | 规则引擎**可预测、可复现**；AI 会猜、会编 |
| 成本 | 零 API 成本，不用管额度、限流、涨价 |
| 定位 | 你做的是**工具**（快、准、可靠），不是**助手** |

**而且规则引擎有一个 AI 做不到的特权：它可以说「我不知道」。**

AI 被设计成总要给出答案，所以它在没把握时会编。规则引擎没命中就是没命中——**这份诚实恰恰是信任的来源**（呼应第三节那 4 条 🔴）。

## 五、数据结构改动建议

`ProjectFix` 现在是个**封闭联合类型**，扩到 20 种会很痛苦。建议改成：

```ts
export interface ProjectFix {
  /** 动作类型：Reopen 能执行 / 只能给指引 */
  action: 'run' | 'guide'
  /** 按钮或提示语（如"帮我装依赖"） */
  label: string
  /** action=run 时：要执行的动作标识 */
  kind?: FixKind
  /** action=guide 时：给用户看的具体做法（命令或链接） */
  detail?: string
}
```

关键区别：**`run` 和 `guide` 是两种东西**，UI 上不应该长得一样。
- `run` → 一个实心按钮，点了就干活
- `guide` → 一个提示框 + 可复制的命令，不假装能一键搞定

**伪装成按钮的引导，比明说是引导更伤人。**

## 六、诊断时机：不止在退出时

现在只在 `child.on('exit')` 里诊断。但有一类失败**进程不退出**：
- 一直重试、一直刷错误
- 卡住不动（等一个永远不来的连接）

建议：在 `processLogs` 的 `onData` 回调里**加一个轻量实时匹配**（只跑正则，命中就标记，不执行动作），`exit` 时连同历史一起判断。

## 七、配方沉淀（L5 的地基）

`recentLogs` 现在是**内存 Map，重启 Reopen 就没了**。

一旦某个项目**修好了、跑起来了**，把「这个项目需要什么」写进项目记录：

```
project.recipe = {
  runtime: 'node@20',
  needsDockerDaemon: true,
  installCmd: 'npm install --legacy-peer-deps',
  envFile: '.env.local',
  lastGoodPort: 5173
}
```

下次启动直接照配方走，**在 D1~D21 之前就避开**。

**这是把「一次性的人工」变成「永久资产」**，也是这类产品唯一能长出护城河的地方。

## 十、开发方案

### 10.1 核心设计：一个纯函数

新增 `src/main/diagnose.ts`——**纯函数、无副作用、可单测**：

```ts
export function diagnose(ctx: {
  logText: string            // 最近日志全文（recentLogs 已有）
  exitCode: number | null
  signal: string | null
  durationMs: number         // ⭐ 存活时长（新信号）
  project: Project           // 类型 / 路径 / 命令 / 端口
}): Diagnosis

export interface Diagnosis {
  code: string                          // 'D5'
  title: string                         // 人话标题：「依赖没装」
  located?: string                      // 定位：「它在找 xxx 模块」
  culprit: 'reopen' | 'user-env' | 'project' | 'external'
  confidence: 'high' | 'low'
  fix?: { action: 'run' | 'guide'; label: string; command?: string }
}
```

**为什么必须是纯函数**：喂一段日志字符串就能断言输出——**规则正确性可以自动化验证**，不用每次手动开 app 试。

**接入点极简**，不破坏现有结构：

```ts
// projectManager.ts:1044 child.on('exit') 分支内
const d = diagnose({ logText, exitCode: code, signal, durationMs, project })
failWithDiagnosis(rt, project, d)   // 内部仍走现有 fail() 通道
```

现有的 `fail(rt, project, reason, fix?)` **原样保留**，只是 `reason` 和 `fix` 改由诊断引擎产出，不再硬编码。**这是纯增量改造。**

### 10.2 规则表驱动（不是 if-else）

```ts
const RULES: Rule[] = [
  {
    code: 'D1',
    match: (t) => /command not found: (\w+)/.exec(t),
    build: (m) => ({
      title: `没装 ${m[1]}`,
      culprit: 'user-env',
      fix: { action: 'run', label: `帮我装 ${m[1]}`, command: `brew install ${pkgOf(m[1])}` }
    })
  },
  // ... 21 条，每条一个数据项
]
```

**加规则 = 加一条数据，不改逻辑。** 跟 `detect.ts` 的表驱动做法一致，维护肌肉记忆是现成的。

### 10.3 三步走（每步可独立上线）

| 步 | 内容 | 风险 | 怎么验证 |
|---|---|---|---|
| **① 骨架 + 兜底** | 建 `diagnose.ts`（先空规则）+ `durationMs` + 兜底文案 + 复制日志按钮 | **零**（不碰任何现有逻辑） | 制造一个规则外的怪错误，看文案是否从「退出码 1」变成人话 |
| **② 前 5 条高频** | D5 依赖没装（迁入）/ D1 命令不存在 / D12 端口被占 / D2 Docker 没起 / D16 语法错误 | 低 | 每条造一个真实失败场景 |
| **③ 全量 + run/guide 分离** | 21 条补全 + `ProjectFix` 结构改造 | 中 | 单元测试全绿 |

**建议先做 ①**：改动最小、覆盖 100% 的失败场景、用户立刻能感觉到差别。

### 10.5 需要拍板的三个点

1. **兜底文案改不改**（步骤①）——会改变现有体验，但这是收益最大的一处
2. **「归属」那一层要不要**——多一层信息，但让小白知道"该找谁"
3. **诊断结果要不要持久化**——为第七节的「配方沉淀」打地基，现在做成本最低

### 12.2 三个被修正的判断

**① TCC 与「原生模块没编译」是同一个根因，且绝不能给一键修复。**

本机日志实测：那份 19471 行的 better-sqlite3 报错日志**同时含有 TCC 特征**——项目在 `~/Downloads` 下，被系统隐私保护挡住，`npm install` 根本写不进 `node_modules`，`.node` 文件才不存在。

若给这类错误挂「帮我装依赖」，用户会**点了失败、再点再失败**，永远出不来。所以 TCC 规则**排在原生模块之前**且**只给 guide 不给 fix**（顺序安全有专门断言守着）。

**② `ProjectFix.action` 最终被独立的 `guide` 字段取代。**

初稿打算在 `fix` 上加 `action: 'run' | 'guide'`。实现时发现语义混了：`fix` 是「点一下我帮你做」，`guide` 是「你得自己做，我告诉你怎么做」——两回事。拆成独立字段后，有 `fix` 出按钮、有 `guide` 出提示框，互不干扰。

**③ `recentLogs` 跨尝试污染必须先修。**

它从不清空（`parseLogPort` 的注释里已承认"旧行里可能还躺着上次的端口"）。诊断若直接吃它，第二次失败时会命中**上一次的报错**——而新的归属徽章会让这个错误结论显得更可信。修法：本轮尝试的日志单独攒进 `Runtime.attemptLogs`，诊断只看这一份。
