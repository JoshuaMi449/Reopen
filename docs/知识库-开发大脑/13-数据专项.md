## 第 13 章：数据专项

### 13.1 是什么

数据专项回答：**"数据存在哪、怎么保命、怎么搬家？"**

### 13.2 存储方案全家桶（从轻到重）

| 方案                              | 人话                                               | 适合                                       |
| --------------------------------- | -------------------------------------------------- | ------------------------------------------ |
| 纯文件（JSON/CSV/YAML）           | 直接存成文本文件，人眼能读、复制即备份             | 数据量小、结构简单的项目（几十上百条记录） |
| SQLite                            | 装在程序里的微型数据库（一个文件），不需要装服务器 | 单机应用、手机 app 的标配                  |
| MySQL / PostgreSQL                | 专业的服务器级关系型数据库                         | 联网服务型产品的标配                       |
| Redis                             | 内存里的极速数据库                                 | 存缓存、排行榜等高频数据                   |
| 对象存储 OSS（AWS S3/阿里云 OSS） | 云上的"网盘服务"，存图片视频大文件                 | 用户上传的文件                             |
| 云数据库                          | 云厂商代管的数据库（不用自己运维）                 | 不想养运维的团队                           |

### 13.3 备份与迁移

| 名词                    | 人话                                                         |
| ----------------------- | ------------------------------------------------------------ |
| 备份 Backup             | 定期把数据复制一份存别处——**没有备份的数据不是资产，是风险** |
| 恢复 Restore            | 从备份把数据救回来                                           |
| 导出/导入 Export/Import | 把数据打包成文件带走/搬进来（换电脑、换软件的救命功能）      |
| 迁移 Migration          | 数据从旧结构搬到新结构（升级版本时改数据格式）               |
| 数据一致性 Consistency  | 数据前后对得上（付了钱订单却没记录 = 不一致）                |

### 13.4 常见误区

- ❌ **数据只在用户本地且没有导出功能**——电脑一坏，用户的数据全没，产品直接背锅。
- ❌ **升级版本改数据格式却不做迁移**——老用户一升级，数据读不出来。
- ❌ **"小数据用数据库"过度设计**——上百条数据用 JSON 文件完全够，杀鸡不用牛刀。

### 13.5 实操要点

**3-2-1 备份原则**（业界通行保命法则）：数据至少 **3 份**，存在 **2 种不同介质**（电脑+移动硬盘），其中 **1 份在异地**（云端）。单机应用的备份就是"导出文件→存云盘"。

**JSON→SQLite 的迁移步骤**（数据格式升级的老坑怎么避）：

1. 新版启动时先检测旧格式数据
2. 备份旧文件（改前先保命）
3. 读旧格式 → 转成新格式 → 写入新存储
4. 验证新数据完整（条数对得上、抽查几条内容一致）再删旧文件
5. 迁移失败要能回滚——所以第 2 步的备份不能省

**导出/导入功能的设计思路**：导出 = 把数据打包成一个文件（用户选保存位置）；导入 = 打开文件校验 → 合并或覆盖（要确认）→ 生效。这是用户换电脑、重装系统的救命功能——**有导出无导入是半残，两者必须成对**。
