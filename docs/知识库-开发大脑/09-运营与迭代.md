## 第 9 章：运营与迭代阶段

### 9.1 是什么

发布之后才是真正的开始：**收集反馈 → 排优先级 → 做下一版 → 再发布**，循环往复（回到[第 1 章](01-全景总览.md)流程图的最底部箭头）。

### 9.2 标准做法

| 名词 | 人话 |
|---|---|
| 数据埋点 Analytics | 在代码里埋"计数点"，统计用户点了哪个按钮、停留多久（开源自托管方案：Umami/Plausible；商业方案：Google Analytics） |
| 用户反馈渠道 | Issue 区、评论区、客服群——产品改进的第一手情报 |
| 迭代节奏 Iteration Cadence | 多久发一版（大厂双周，个人项目按需） |
| Roadmap 路线图 | 未来几个月计划做什么的公开地图 |
| 用户留存 Retention | 用户用了还会不会回来（产品的生死指标） |

### 9.3 开源治理专项

开源项目有一套社区规范：

| 名词 | 人话 |
|---|---|
| License 开源协议 | 规定"别人能用你的代码干什么"的法律文本。三大件：**MIT**（最宽松：随便用，保留署名即可）、**Apache 2.0**（宽松+专利保护）、**GPL**（严格：用了你的代码，他的代码也必须开源） |
| README | 仓库首页的说明书：项目是什么、怎么装、怎么用（开源项目的门面） |
| Contributing 指南 | 告诉想参与的人"怎么贡献代码"（怎么提 Issue、怎么提 PR） |
| Issue 模板 / PR 模板 | 提前写好的提问格式，让反馈规范可读 |
| Star / Fork / Watch | GitHub 三连：收藏 / 复制到自己名下 / 订阅动态（开源项目的"人气值"） |
| Code of Conduct | 社区行为守则 |

### 9.4 常见误区

- ❌ **发布完就撒手**——开源项目的价值一半在产品、一半在持续维护的信任感。
- ❌ **License 不选或乱选**——不选 License 默认"保留所有权利"，别人想用都不敢用。
- ❌ **README 只有两行字**——路人 30 秒看不懂这项目是干嘛的，就走了。

### 9.5 指标与分析

**核心指标体系**（怎么算、什么算好）：

| 指标 | 怎么算 | 人话 |
|---|---|---|
| DAU/MAU | 日活跃用户 / 月活跃用户 | 每天/每月多少人在用；DAU/MAU 比值越高粘性越强 |
| 留存率 Retention | 第 N 天还在用的比例 | "用户会不会回来"——留存曲线前 7 天陡降是常态，看 30 天留存才是真章 |
| 转化率 Conversion | 走完某一步的用户比例 | 下载→安装→首次使用→活跃，每一步的流失点在哪 |
| 漏斗 Funnel | 转化率的串联视图 | 每一步剩多少人，最陡的落差就是最该修的地方 |
| NPS | "你会推荐给朋友吗"0-10 分 | 9-10 分是推荐者，6 分以下贬损者——净推荐值 |
| OKR | 目标+关键结果 | 团队定目标的方法："这个季度 O1：增长用户；KR1：DAU 到 1000" |

**北极星指标**：整个产品只盯一个核心指标（如"每周成功复活的次数"），所有功能都为它服务——指标多了会打架。

**埋点设计原则**：埋**行为事件**（什么时候、谁、做了什么、带什么属性），不埋隐私数据；先想清楚"我要回答什么问题"，再埋对应事件——埋了不看的点都是噪音。
