## 第 5 章：开发阶段（程序员的世界）

> 这是八个阶段里的**重头戏**，也是名词最密集的一章。写代码的全部家当都在这里。

### 5.0 编程基础（看懂 AI 写代码的地基）

看 AI 写代码不需要自己会写，但需要看懂它在干什么。这五个概念是地基：

#### ① 数据结构：数据怎么放

| 结构              | 人话                           | 什么时候用               |
| ----------------- | ------------------------------ | ------------------------ |
| 数组 Array        | 一排格子，按编号（下标）取     | 存一串东西，如"5 个项目" |
| 栈 Stack          | 一摞盘子，后放先拿（后进先出） | 撤销/重做、函数调用      |
| 队列 Queue        | 排队，先进先出                 | 任务排队、消息队列       |
| 哈希表 Hash Table | 拿着名字直接找到座位           | 按名字查数据，"查"最快   |
| 树 Tree           | 一层套一层的层级结构           | 文件夹、菜单、组织架构   |

#### ② 算法复杂度：为什么有的代码慢

"复杂度"不是代码多复杂，而是**数据变多时代码会变慢多少**，用大 O 表示：

| 记号  | 人话                       | 例子                 |
| ----- | -------------------------- | -------------------- |
| O(1)  | 不管多少数据，都是固定一步 | 哈希表按名字查       |
| O(n)  | 数据翻倍，时间翻倍         | 从头到尾找一遍       |
| O(n²) | 数据翻倍，时间变四倍       | 两两比较（嵌套循环） |

人话：数据量一大，O(n²) 的代码会卡死，O(1) 的代码纹丝不动——这就是为什么"查得快不快"要问数据是怎么存的。

#### ③ 作用域与闭包

- **作用域（Scope）**：变量在哪个范围里"可见"。函数里的变量外面看不到——像房间里的东西，出了房间就拿不到
- **闭包（Closure）**：函数"记着"它出生时的房间——就算离开了那个范围，还能用到当时的变量。React 的 Hook 大量依赖闭包，看到"闭包"二字不用慌：就是"函数带着老家记忆"

#### ④ 字符编码：乱码从哪来

电脑只认数字，文字要按"对照表"翻译成数字——这张表就是**字符编码**：

- **UTF-8**：现在的全球标准，中英文混排都不乱
- 乱码的成因：读的人用了和写的人不一样的对照表（比如用 GBK 打开 UTF-8 文件）
- 口诀：**所有文件统一 UTF-8**，乱码基本绝迹

#### ⑤ 设计模式：前人总结的套路

设计模式 = 常见问题的**标准解法**，知道名字就能和 AI 高效沟通：

| 模式            | 人话                                                | 什么时候用                                   |
| --------------- | --------------------------------------------------- | -------------------------------------------- |
| 单例 Singleton  | 全局只允许一个实例                                  | 应用本体、配置中心（桌面应用的单例锁就是它） |
| 观察者 Observer | 一处变化，所有订阅者自动收到通知                    | 事件监听、状态变化联动                       |
| 工厂 Factory    | 一个"生产车间"按需造对象                            | 多种相似对象统一创建                         |
| MVC             | 界面（View）/逻辑（Controller）/数据（Model）分三层 | 几乎所有有界面的应用底层都是它               |

#### ⑥ 异步：单线程为什么能同时干很多事

JS 是**单线程**——同一时刻只干一件事。但它靠**事件循环（Event Loop）**不卡界面：把慢活（读文件、等网络）丢到"后台排队"，干完再回来处理结果（Promise 的 async/await 语法就是管理这件事的）。

人话：一个厨子（单线程），把炖汤（慢活）放火上（后台），继续切菜（干别的），汤好了响铃（事件循环通知）再去盛——全程没干等。看到 `async`/`await`/`Promise`，就是在"等慢活干完的通知"。

### 5.1 前端开发

**前端（Frontend）** = 用户看得见的部分：画面、按钮、动画。在网页里是网页本身，在桌面应用里是应用窗口里的界面。

#### 5.1.1 前端三件套

所有前端界面，不管多复杂，底层都是这三样：

| 技术             | 全称                      | 人话                             | 类比         |
| ---------------- | ------------------------- | -------------------------------- | ------------ |
| HTML             | HyperText Markup Language | 搭骨架：标题、段落、按钮摆在哪   | 房屋的梁和墙 |
| CSS              | Cascading Style Sheets    | 化妆：颜色、字体、大小、间距     | 墙漆和家具   |
| JavaScript（JS） | —                         | 行为：点按钮发生什么、数据怎么变 | 水电开关     |

#### 5.1.2 TypeScript（TS）

**TypeScript** = JavaScript 的加强版，多了一个"**类型（Type）**"系统。

人话：JS 就像菜市场喊价，说几就是几，写错了一运行才炸；TS 给每个数据贴上"类型标签"（这个是数字、那个是字符串），**在写代码时就拦住大部分低级错误**。标签不影响运行，但让代码更稳、AI 写起来也更不易出错。

| 名词                   | 人话                                                       |
| ---------------------- | ---------------------------------------------------------- |
| 类型 Type              | 数据的"身份标签"：number 数字 / string 文本 / boolean 真假 |
| 类型检查 Type Checking | 自动核对"标签对不对"的体检（工具：tsc）                    |
| any                    | 放弃贴标签的类型，等于放弃体检（能用但别滥用）             |

#### 5.1.3 前端框架（以 React 为例）

直接写三件套能做小页面，但界面一复杂就要用**框架（Framework）**——别人搭好的半成品骨架。主流三大家：**React**、**Vue**、**Angular**（React 使用者最多）。

以 React 为例的核心名词：

| 名词           | 人话                                                                         |
| -------------- | ---------------------------------------------------------------------------- |
| 组件 Component | 界面的"积木块"：一个按钮、一张卡片、一个弹窗各是一个组件，像乐高一样拼出页面 |
| 状态 State     | 组件"记着的当下情况"：开关是开是关、列表里有几条                             |
| 属性 Props     | 组件之间的"参数传递"：把标题文字传进卡片组件                                 |
| 钩子 Hook      | 组件能力的"外挂接口"（useState 管状态、useEffect 管时机）                    |
| JSX            | 在 JS 里直接写界面标签的语法（HTML 和 JS 混写）                              |
| 路由 Router    | 管"用户点哪里跳到哪个页面"的导航系统                                         |
| 虚拟 DOM       | React 的提速技巧：先在内存里算好改哪，再一次性改真实界面                     |

#### 5.1.4 包管理器与依赖

| 名词                          | 人话                                                                 |
| ----------------------------- | -------------------------------------------------------------------- |
| 依赖 Dependency               | 项目"借用"的别人写好的库（如日期处理库），自己不用重写               |
| 包 Package                    | 一个可安装的库的最小单位                                             |
| npm / pnpm / yarn             | 三个包管理器（"借书系统"）：帮你下载、安装、管理依赖                 |
| package.json                  | 项目的"身份证+借书单"：记录项目叫什么、借了哪些库、有哪些命令        |
| node_modules                  | 借来的库堆放的文件夹（很庞大，一般不上传代码库）                     |
| lockfile（package-lock.json） | "借书清单锁定版"：保证所有人装的版本一模一样                         |
| 依赖漏洞                      | 借来的库自带安全洞，需要定期检查更新（见[第 10 章](10-安全专项.md)） |

#### 5.1.5 构建工具

浏览器/桌面壳只认"加工好的成品"，而开发者写的是"原料"。中间的加工厂叫**构建工具（Build Tool）**：**Vite**（新一代，快）和 **Webpack**（老牌）是主流。

| 名词                                 | 人话                                                |
| ------------------------------------ | --------------------------------------------------- |
| 开发服务器 Dev Server                | 构建工具自带的本地预览服务（改代码立刻看效果）      |
| 热更新 HMR（Hot Module Replacement） | 改一行代码，界面**不刷新**就地更新（改哪里变哪里）  |
| 打包 Bundle                          | 把成百上千个源文件加工成几个成品文件                |
| 压缩 Minify                          | 去掉空格注释、缩短变量名，成品文件变小变快          |
| 构建产物 Build Output                | 加工好的成品文件夹（dist/ 或 out/），交付给打包环节 |

### 5.2 后端开发

**后端（Backend）** = 用户看不见的部分：逻辑、数据、接口。前端问后端要数据，后端算好给前端。

| 名词                    | 人话                                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| 后端语言 Java           | 老牌企业级：银行/大厂服务器主力，Android 也用。稳但啰嗦                                        |
| 后端语言 Python         | 解释型"万能胶"：代码像白话，脚本/爬虫/AI/自动化首选，新手第一语言                              |
| 后端语言 Go             | 编译型，Google 出品：写法简单、跑得快，天生适合服务器和工具                                    |
| 后端语言 Node.js        | 严格说是"运行环境"：让 JS 脱离浏览器跑在服务器上，一门语言前后端通吃                           |
| 后端语言 PHP            | 最早的"做网站专用"语言，WordPress 等大量老网站用它                                             |
| 后端语言 Ruby           | "让程序员开心"的语言，配 Rails 做出过一代明星网站，现在小众                                    |
| 后端框架                | Spring（Java）、Django/Flask（Python）、Express（Node.js）——框架帮你处理收请求、发响应这些杂活 |
| 业务逻辑 Business Logic | 产品规则的代码化："满 100 减 20"、"库存不足不能下单"                                           |
| 中间件 Middleware       | 请求进来后先过安检（登录校验、日志记录），再进业务                                             |
| ORM                     | 把数据库的表格包装成代码里的对象，写代码不用手拼数据库语言                                     |
| Cookie                  | 网站存在你浏览器里的"小纸条"（记住你是谁、你的偏好）                                           |
| Session 会话            | 服务器端记着的"你这次访问的状态"（登录状态就靠它）                                             |
| 消息队列 Message Queue  | 任务排队的"中转站"（RabbitMQ/Kafka）：下单后发短信这类慢活先排队，前台先返回                   |
| WebSocket               | 长连接的实时通信：服务器有新消息**主动推**给页面（聊天、实时刷新都靠它）                       |

> **注意**：不是所有产品都需要后端。**单机工具**（不联网、数据存本机）可以把"后端"浓缩在应用内部，不需要服务器。判断标准只有一个：**数据要不要跨设备共享**。要共享 → 必须有后端服务器；不用共享 → 可以没有。

### 5.3 桌面应用开发专项

桌面应用（双击图标打开窗口的那种）除了前端那套，还有一套自己的名词。主流技术分两派：**Electron**（用网页技术做桌面应用）和 **Tauri**（网页界面+更轻的壳）。

#### 5.3.1 Electron 的核心机制

| 名词                               | 人话                                                                                             |
| ---------------------------------- | ------------------------------------------------------------------------------------------------ |
| Chromium                           | Google 开源的浏览器内核。Electron 把整个浏览器内核打包进应用——所以界面和网页一样好写，代价是包大 |
| Node.js                            | 让 JS 脱离浏览器、能操作电脑（读写文件、跑命令）的运行环境                                       |
| 主进程 Main Process                | "总管进程"：和操作系统打交道（弹窗口、读文件、启动外部程序），一个应用只有一个                   |
| 渲染进程 Renderer Process          | "界面进程"：画界面、响应点击，每个窗口一个                                                       |
| Preload 预加载脚本                 | 渲染进程和主进程之间的"安全门岗"，只放行允许的传话                                               |
| IPC（Inter-Process Communication） | 进程间通信，两个进程之间的"对讲机"                                                               |
| BrowserWindow 浏览器窗口           | Electron 里窗口的对象叫法                                                                        |

**为什么分两个进程？** 界面进程（渲染进程）随便折腾，哪怕卡死，总管进程（主进程）照常干活、其他窗口不受影响；反过来，总管进程一旦崩溃，整个应用会退出——所以总管进程要尽量简单、少出问题。这是桌面应用稳定性的基石。

**Electron 的安全底线**（单机应用也要守住的三条）：

| 配置                  | 人话                                                       |
| --------------------- | ---------------------------------------------------------- |
| contextIsolation 开启 | 渲染进程与系统能力隔离——界面被注入恶意代码也拿不到系统权限 |
| nodeIntegration 关闭  | 渲染进程不直接暴露 Node 能力                               |
| IPC 通道最小化        | 两个进程之间只开必要的"传话通道"，不开后门                 |

人话：浏览器内核是"公共场所"（可能加载外部内容），系统权限是"家里钥匙"——安全底线就是不让公共场所的人摸到钥匙。

#### 5.3.2 打包与分发

| 名词                   | 人话                                                  |
| ---------------------- | ----------------------------------------------------- |
| 打包 Packaging         | 把代码+内核+图标做成安装包                            |
| electron-builder       | Electron 生态最流行的打包工具，一条命令出全平台安装包 |
| dmg                    | macOS 的安装包格式（双击那个磁盘图标）                |
| exe / NSIS 安装器      | Windows 的安装包格式                                  |
| AppImage               | Linux 的绿色包格式                                    |
| 绿色版/便携版 Portable | 不用安装、解压即用的版本                              |

#### 5.3.3 签名与公证（macOS 专属痛点）

| 名词                             | 人话                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------- |
| 代码签名 Codesigning             | 给应用盖"生产厂商章"，证明没被篡改                                           |
| 公证 Notarization                | 苹果官方检查一遍后放行——没公证的应用，用户双击会弹"无法验证开发者，无法打开" |
| 开发者证书 Developer Certificate | 签名要用的"章"，个人开发者账号 99 美元/年                                    |
| Gatekeeper                       | macOS 的"门卫"系统，只放行签名过的应用                                       |
| SmartScreen                      | Windows 的同类门卫                                                           |
| 自签名 Self-signed               | 自己给自己刻章（没花钱的章）——门卫仍会警告，但可右键强制打开                 |

**个人开源项目的务实做法**：免费阶段用自签名/不签名分发，在说明文档里写清"如何打开"；有条件（99 美元/年）再正式签名公证。

#### 5.3.4 桌面应用特有的系统能力

| 名词                              | 人话                                                                                                    |
| --------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 托盘 Tray                         | 菜单栏/任务栏右下角的小图标，应用可常驻后台                                                             |
| 开机自启 Auto-launch              | 登录系统后自动启动。macOS 用 launchd（LaunchAgent 配置），Windows 用注册表/任务计划                     |
| 自动更新 Auto Update              | 应用自己检测新版本并更新（Electron 用 electron-updater），更新包通常托管在 GitHub Releases 或自建服务器 |
| 全局快捷键 Global Shortcut        | 在系统任何地方按组合键唤起应用                                                                          |
| 应用内快捷键 Accelerator          | 应用内部的快捷键（⌘S 保存、⌘F 搜索），和全局快捷键是两套体系                                            |
| 通知 Notification                 | 系统通知中心弹消息                                                                                      |
| Dock 程序坞                       | macOS 底部图标栏：图标常驻、右键弹出快捷菜单、跳动提醒                                                  |
| 菜单栏应用 Menu Bar App           | 只在屏幕顶部菜单栏显示图标的常驻小工具（和托盘 Tray 同族不同形态）                                      |
| 文件关联 File Association         | 双击某个后缀的文件自动用你的应用打开（如 .md 关联到编辑器）                                             |
| 自定义 URL 协议 Custom URL Scheme | 注册 `myapp://` 链接，从浏览器/其他应用唤起本应用                                                       |
| Keychain 钥匙串                   | macOS 系统级密码保险库，存 Token/密码比明文写配置文件安全                                               |
| TCC 权限体系                      | macOS 的隐私权限管理（摄像头/文件夹访问弹窗就归它管）                                                   |
| App Sandbox 沙盒                  | macOS 把应用限制在专属区域运行的机制，上 App Store 强制要求                                             |
| 单例锁 Single Instance Lock       | 防止用户开两个实例打架：第二个实例启动时自动唤起第一个                                                  |
| 守护进程 Daemon                   | 后台常驻、没有界面的服务进程（区别于管多个服务的 pm2）                                                  |
| 健康检查 Health Check             | 定期自检"还活着吗、端口还通吗"的动作，启动服务后探活也用它                                              |
| 端口占用/冲突 Port Conflict       | 两个程序抢同一个端口号导致启动失败，报错"Address already in use"就是它                                  |
| 配置文件 Config File              | 用户设置存哪：macOS 规范位置是 ~/Library/Application Support/应用名/                                    |

### 5.4 脚本与命令文件专项（"run 什么命令的文件"）

用户问过的"开发里经常看到 run 什么命令，都是什么文件"——这一节全部讲清。

#### 5.4.1 终端与命令行

| 名词                          | 人话                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| 终端 Terminal                 | 那个黑框框窗口，用打字的方式指挥电脑                                                 |
| Shell                         | 终端里解释你命令的"翻译官"：macOS/Linux 用 bash 或 zsh，Windows 用 PowerShell 或 cmd |
| 命令 Command                  | 你打的一行字："启动服务""复制文件"                                                   |
| CLI（Command Line Interface） | 命令行工具的总称（相对 GUI 图形界面而言）                                            |

#### 5.4.2 各种"命令文件"一览

| 文件                                   | 人话                                                                                                 |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| package.json 的 scripts 段             | JS 项目里定义"常用命令的别名"：`npm run dev` 里的 dev 就是在这里定义的。一条别名背后可以是一长串命令 |
| Shell 脚本 .sh                         | 一连串命令写成的"批处理剧本"（macOS/Linux），双击/执行即按剧本跑                                     |
| 批处理 .bat                            | Windows 版的脚本剧本                                                                                 |
| Makefile                               | 老牌命令别名文件（C 生态常用）                                                                       |
| .env 文件                              | 存"环境变量"的隐藏文件：密码、密钥、配置项（数据库地址等），不上传代码库                             |
| 环境变量 Environment Variable          | 系统级的"全局配置开关"，程序启动时读取                                                               |
| PATH                                   | 特殊环境变量：系统去哪找可执行程序（装新工具就是把它加进 PATH）                                      |
| CI 配置文件（.github/workflows/*.yml） | 告诉 GitHub"代码一提交就自动帮我跑哪些命令"（详见[第 7 章](07-运维阶段.md)）                         |

**常见命令速查**（JS 生态）：

- `npm install` / `pnpm install` —— 按 package.json 借书（装依赖）
- `npm run dev` —— 跑开发模式（起本地预览服务）
- `npm run build` —— 跑构建（出成品）
- `npm run test` —— 跑测试
- `npm run dist` —— 打包安装包

### 5.5 Git 版本管理

**Git** 是"代码世界的时光机 + 多线协作器"。**GitHub 是一个托管 Git 仓库的网站**——Git 是工具，GitHub 是放代码的网站（两者常被混为一谈）。

| 名词                        | 人话                                              |
| --------------------------- | ------------------------------------------------- |
| 仓库 Repository（repo）     | 一个项目的"档案库"，存所有代码和全部历史版本      |
| 本地仓库 / 远程仓库         | 自己电脑上的档案库 / GitHub 上的档案库            |
| 克隆 Clone                  | 把远程仓库复制一份到本地                          |
| Fork                        | 把别人的仓库复制成自己的（开源协作第一步）        |
| 提交 Commit                 | 一次"存档"：当前改动打包成一个版本，附一句说明    |
| 暂存区 Staging              | 选好"这次存档要包含哪些改动"的篮子                |
| 分支 Branch                 | 一条独立的开发线（主干旁开岔道），互不干扰        |
| 主分支 main / master        | 主干道，放稳定代码                                |
| 功能分支 Feature Branch     | 每个功能开一条岔道，做完合回主干                  |
| 合并 Merge                  | 把岔道并回主干                                    |
| 冲突 Conflict               | 两条线改了同一个地方，合并时"打架"，需要人工裁决  |
| 拉取请求 PR（Pull Request） | "我这条岔道做完了，请审阅后合并进主干"的正式申请  |
| 代码审查 Code Review        | 合并前同事逐行审代码，挑毛病（规范、逻辑、隐患）  |
| 推送 Push / 拉取 Pull       | 本地仓库和远程仓库之间的同步动作                  |
| .gitignore                  | 声明"哪些文件不进档案库"（如 node_modules、.env） |
| Tag 标签                    | 给某个存档起名（如 v1.0.0），发布版常用           |
| Release                     | GitHub 上的"正式发布"，可附安装包下载             |

**提交信息规范（Conventional Commits）**——存档说明有标准格式：

- `feat: 添加项目登记功能`（新功能）
- `fix: 修复开机自启失效`（修 bug）
- `docs: 更新使用说明`（文档）
- `chore: 升级依赖`（杂务）

**版本号语义化（SemVer）**——`1.2.3` 三位数字各司其职：

- 第 1 位（主版本 Major）：大改版，不兼容旧版（1.0 → 2.0）
- 第 2 位（次版本 Minor）：加了新功能，仍兼容（1.1 → 1.2）
- 第 3 位（补丁 Patch）：只修 bug（1.2.2 → 1.2.3）

### 5.6 代码质量

| 名词                       | 人话                                                         |
| -------------------------- | ------------------------------------------------------------ |
| ESLint                     | 代码规范检查器：写得不规范（少分号、声明了没用）当场标黄标红 |
| Prettier                   | 代码格式化器：一键把代码排版得整整齐齐                       |
| Lint（统称）               | "查规范"这件事：代码没 bug 但丑/乱/有隐患，lint 来管         |
| 静态检查 Static Analysis   | 不运行代码，靠"读代码"找出问题（类型检查属于其中）           |
| 代码规范 Style Guide       | 团队约定的写法规则（缩进几个空格、变量怎么命名）             |
| 注释 Comment               | 代码里写给人类看的说明文字                                   |
| 命名规范 Naming Convention | 变量函数怎么起名（如小驼峰 camelCase）                       |
| 技术债 Technical Debt      | "为了赶工写得糙，以后要还的账"——欠债要记账，不能装看不见     |

**正规团队的代码质量铁律**：lint 不过不让合并；没有 Code Review 不让合并；测试挂了不让合并。

**技术债的治理**（单人项目同样适用）：

| 原则       | 人话                                                         |
| ---------- | ------------------------------------------------------------ |
| 欠债要记账 | 发现糙代码，写进台账（"某处赶工，需重构"）——看不见的债最危险 |
| 还债要定时 | 每个版本留一点时间还债，别等债滚成高利贷（改一处崩三处）     |
| 重写前先问 | "重写它比改它还便宜吗"——不是所有糙代码都值得还               |
| 别欠新债   | 改旧代码时顺手把明显的糙处抹平（顺手，不是大动干戈）         |

### 5.7 开发阶段的协作铁律

1. **每天提交**：小步快跑，改一点存一点，坏了随时回到上一个存档
2. **一条分支一个功能**：互不干扰，坏了不影响主干
3. **提交信息写清楚**：三个月后自己都看得懂"这次改了什么"
4. **先写测试再写功能**（可选进阶）：用测试定义"什么是做对了"，写完代码测试通过即完成

### 5.8 常见误区

- ❌ **"我代码能跑就是好代码"**——能跑 ≠ 可维护。三个月后看不懂自己的代码 = 没有维护性。
- ❌ **什么都自己写，不借用依赖**——重复造轮子是最大的浪费；但依赖太多也是风险（见[第 10 章](10-安全专项.md)漏洞扫描）。
- ❌ **不提交、不存档**——代码没进 Git 仓库就等于裸奔，硬盘一坏全完。
- ❌ **提交信息写"更新""改了一点"**——这种存档说明三个月后毫无用处。

### 5.9 开发者的日常工具与工作方式

写代码的日常"装备"和"招式"：

| 名词             | 人话                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| IDE 集成开发环境 | 写代码的"高级工作台"：编辑器+查错+调试+运行一体化。**VS Code** 是当下最流行的（免费、插件海量） |
| 编辑器 Editor    | 纯写代码的软件（IDE 的简化版）                                                                  |
| 调试 Debug       | 找 bug 的过程："程序在哪一步坏了、为什么坏"                                                     |
| 断点 Breakpoint  | 调试时在代码某一行"设卡"，程序跑到这里暂停，让你检查现场                                        |
| 日志调试         | 在代码里打 `console.log`（打印一行状态到控制台），看程序走到哪、值是什么——最朴素的调试法        |
| 控制台 Console   | IDE 里显示日志输出的面板                                                                        |
| nvm / fnm        | Node.js 版本管理器：一台电脑装多个 Node 版本，按项目切换（不同项目依赖不同版本）                |
| 联调 Joint Debug | 前后端把两边接上一起调试："你调接口我调页面，边连边修"                                          |

**一个 bug 的标准排查流程**：复现问题 → 看日志/控制台输出 → 在可疑处打断点 → 逐步运行观察变量 → 定位出错行 → 修复 → 跑测试确认。
