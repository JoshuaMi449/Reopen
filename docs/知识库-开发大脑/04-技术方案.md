## 第 4 章：技术方案阶段（架构师的世界）

### 4.1 是什么

技术方案阶段回答一个问题：**"用什么技术、怎么搭？"**

需求说清了"做什么"、设计画出了"长什么样"，技术方案定"怎么做出来"。这个阶段是纯技术决策，但好架构师会把每个决策**用人话讲给非技术的人听**，因为技术方案直接影响工期、成本、以后好不好改。

### 4.2 标准做法：技术选型的三个标准

**技术选型（Technology Selection）** = 选编程语言、选框架、选数据库。正规团队用三个标准打分：

| 标准 | 人话 | 举例 |
|---|---|---|
| 生态成熟度 | 这技术有没有很多人用？出了问题搜不搜得到答案？ | 用的人多 = 坑都被人踩过了 |
| 执行者能力 | 写代码的人（团队或 AI）熟不熟这个技术？ | 会 Java 的团队硬上 Go，工期翻倍 |
| 目标平台 | 这个东西跑在什么设备上？ | 只跑苹果设备才能选 Swift；要跨平台就排除它 |

选型是**取舍**，没有"最好的技术"，只有"最适合这个项目+这批人"的技术。

### 4.3 标准做法：架构设计

**架构（Architecture）** = 代码世界的"房屋结构图"：分几层、分几块、块和块之间怎么传话。架构决定"以后改功能是动一面墙还是拆整栋楼"。

三个通用概念：

| 名词 | 人话 |
|---|---|
| 分层架构 Layered Architecture | 从上到下分层：界面层（给人看的）→ 业务层（干活的逻辑）→ 数据层（存取数据）。下层不认识上层，改界面不影响逻辑 |
| 前后端分离 Frontend/Backend Separation | 前端（界面）和后端（逻辑+数据）分成两个独立工程，靠 API 传话。好处：两边各改各的 |
| 模块化 Modularization | 按功能拆成独立小房间（模块），每个模块职责单一，坏了只修一个房间 |

反面教材：**单体架构（Monolith）** = 所有代码混在一大坨里，改一处牵全身——项目小的时候省事，大了就是灾难。**微服务（Microservices）** = 拆成几十个独立小服务各自部署——大厂才需要，个人项目用是过度设计。

### 4.4 标准做法：数据库设计

**数据库（Database）** = 专门存取数据的"仓库软件"。设计数据库 = 设计仓库里有哪些表格、每张表有哪些列。

| 名词 | 人话 |
|---|---|
| 表 Table | 一张表格（如"用户表""订单表"） |
| 字段 Field / 列 Column | 表格的一列（如"用户名""手机号"） |
| 记录 Record / 行 Row | 表格的一行（一个用户的信息） |
| 主键 Primary Key | 每行唯一的身份证号（ID） |
| 外键 Foreign Key | 指向另一张表某行的"引用"（订单表里的"用户ID"） |
| 索引 Index | 给表格建目录，查询变快（书里的目录页） |
| 关系型数据库 | MySQL、PostgreSQL 这类：表之间有明确关联，数据严格整齐 |
| 非关系型数据库（NoSQL） | MongoDB 这类：数据灵活松散，适合结构不固定的数据 |

数据量小的项目也可以不用数据库软件，直接用**文件**存数据（JSON/CSV），简单透明。

**索引与事务的原理**（两个最容易误用的概念）：

| 概念 | 人话 |
|---|---|
| 索引原理 | 给列建"目录页"：数据库按目录直接定位，不用全表翻一遍。**代价**：每次新增/修改数据都要同步更新目录，写会变慢——所以索引加在"经常查、很少改"的列上 |
| 事务 ACID | 一组操作打包成"要么全成功、要么全回滚"：A 转账给 B，扣 A 的钱和加 B 的钱必须同生共死，不能扣了钱没到账 |
| 事务隔离级别 | 多个事务同时跑时"互相看得见多少"的档位（读未提交/读已提交/可重复读/串行）。人话：档位越严格越安全但越慢；转账扣款这类用最严格档，普通查询用默认档即可 |
| 死锁 | 两件事互相等对方放资源，谁都动不了。数据库会自动检测并杀掉一个来解开 |

**什么时候需要事务**：涉及"两步必须同生共死"的操作（转账、扣库存下单、迁移数据）。只读操作不需要。

### 4.5 标准做法：API 设计

**API（Application Programming Interface，应用程序接口）** = 两个程序之间约定的"传话规则"。

人话版：你去银行柜台，只能按银行规定的格式办事（填单子、报卡号），柜台才给你办。API 就是这个"规定格式"——程序 A 按格式发请求，程序 B 按格式给回应。

| 名词 | 人话 |
|---|---|
| 请求 Request | 你发出的"我要办什么" |
| 响应 Response | 对方回的"办好了/办不了" |
| HTTP 方法 | 办事的种类：GET（查询）/ POST（新增）/ PUT（整体替换）/ PATCH（部分修改）/ DELETE（删除） |
| 状态码 Status Code | 结果的数字代号：200 成功 / 201 创建成功 / 400 你请求写得不对 / 401 没登录 / 403 没权限 / 404 找不到 / 500 服务器自己挂了 |
| RESTful | 一种流行的 API 设计风格，用"名词当网址、动词用 HTTP 方法" |
| 第三方服务集成 | 常见"接线"对象：**支付**（微信支付/支付宝/Stripe）、短信验证码、地图、第三方登录（OAuth）——都是对方提供 API，你照着接口文档接 |
| JSON | 数据交换的标准格式，长得像 `{"名字": "小明", "年龄": 30}` |
| 接口文档 API Docs | 记录所有 API 用法的说明书（工具：Swagger/OpenAPI） |

**API 设计 = 前后端的合同**：后端写好接口文档，前端照着开发，两边不必等对方——这是多人协作能并行的关键。

**三个高频网络概念**（和 API 打交道绕不开）：

| 概念 | 人话 |
|---|---|
| HTTP 缓存 | 浏览器"问一句：内容变了吗"（ETag 指纹比对）或"这个内容 N 秒内直接用自己的存档"（Cache-Control 有效期），不变就不重新下载——网页快的秘密之一 |
| CORS 跨域 | 浏览器安全规则：A 网站的页面默认不能调 B 网站的接口（防止恶意网站偷数据）。解决：B 的服务器声明"允许 A 来调"（响应头加允许名单） |
| JWT | "带签名的通行证"：登录后发一串加密字符串（里面装着"你是谁+过期时间+签名"），之后每次请求带着它，服务器验签名就知道你是谁——无状态、不用服务器记会话 |

### 4.6 常见误区

- ❌ **技术方案追求时髦**——"别人用了新框架我也要"。选型的第一标准是"执行者熟不熟、生态成不成熟"，不是新不新。
- ❌ **架构过度设计**——10 个用户的产品按 1 亿用户设计，纯浪费。架构复杂度要配得上项目规模。
- ❌ **不做接口文档**——没有文档的 API 就是口头约定，联调时互相甩锅。
- ❌ **技术方案不翻译给人听**——技术负责人如果解释不清"为什么这么选"，这个方案大概率是拍脑袋。

### 4.7 架构演进与治理

#### 单体 → 微服务的演进

| 形态 | 人话 | 什么时候合适 |
|---|---|---|
| 单体 Monolith | 一个应用包下所有功能 | 几乎所有项目一开始都该这样——简单、好调试 |
| 微服务 Microservices | 每个功能一个独立服务，各自部署 | 团队几十人、功能互相独立、需要独立扩容时再拆 |

**拆分判据**（缺一不可）：功能边界清晰 + 团队足够大（能独立负责）+ 部署频率差异大。**个人项目永远单体**——微服务是大厂的药，不是个人的。

#### 高可用三板斧（服务型产品）

| 手段 | 人话 |
|---|---|
| 限流 Rate Limiting | 每人每秒最多 N 次请求，超了拒绝——防刷防雪崩 |
| 熔断 Circuit Breaker | 下游服务挂了，立刻停止调用它（像电闸跳闸），等它恢复再试 |
| 降级 Degradation | 出事时砍掉次要功能保核心（"图片不加载了但支付还能用"） |

#### 缓存策略

| 概念 | 人话 |
|---|---|
| LRU 淘汰 | 缓存满了，把最久没用的踢出去 |
| 缓存穿透 | 查一个数据库里根本没有的数据，每次都穿到数据库——解决：把"没有"也缓存 |
| 缓存雪崩 | 一大批缓存同时过期，请求全砸到数据库——解决：过期时间加随机抖动 |

#### 仓库策略：Monorepo vs 多仓库

- **Monorepo**：所有项目放一个仓库（Vite 生态主流）——改依赖方便、全局搜索容易
- **多仓库**：一个项目一个仓库——权限清晰、历史干净
- 个人项目：一个项目一个仓库最简单；除非有共享代码库需求，才考虑 Monorepo
