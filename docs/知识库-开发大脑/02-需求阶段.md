## 第 2 章：需求阶段（产品经理的世界）

### 2.1 是什么

需求阶段回答一个问题：**"我们到底要做什么？"**

把人话的"我想要个东西"变成开发团队能照着干的"合同"。这个阶段最重要的产出物是 **PRD**。

### 2.2 标准做法：PRD 详解

**PRD（Product Requirements Document，产品需求文档）** 是整个项目的"宪法"：产品经理写、开发照着做、测试照着验、扯皮时翻它。一份正规 PRD 包含八个部分：

**① 背景与目标**
- 人话：为什么做这个东西？解决谁的什么痛苦？
- 关键名词：**痛点（Pain Point）**——用户难受的地方；**目标用户（Target User）**——给谁用
- 标准写法：一句话说清"帮助____（谁）解决____（什么问题），达到____（什么效果）"

**② 用户与场景**
- 人话：用户在什么情况下会用你的产品？
- 关键名词：**使用场景（Use Case）**——"周末下午，我打开电脑想继续上周的项目，却发现找不到服务了"这种具体描述
- 标准写法：列出 3-10 个典型场景，每个场景一两句话

**③ 功能清单（按优先级）**
- 人话：要做什么功能，先做哪个后做哪个
- 关键名词：**优先级（Priority）**、**P0/P1/P2**（见 2.4）、**MVP（Minimum Viable Product，最小可行产品）**——能解决核心痛点的最少功能集，先做 MVP 是个人项目的黄金法则

**④ 页面清单与交互说明**
- 人话：有哪些界面？每个界面上有什么？点了会怎样？
- 标准写法：一页一页列——"首页：顶部一个搜索框，中间是列表，点列表项进入详情页"
- 名词见[第 3 章](03-设计阶段.md)

**⑤ 非功能需求**
- 人话：除了"有什么功能"之外的要求
- 关键词：**性能**（快不快）、**兼容性**（哪些设备能用）、**安全性**、**稳定性**
- 标准写法："应用启动时间不超过 3 秒""支持 macOS 12 以上"这类可量化的句子

**⑥ 验收标准**
- 人话：做到什么程度算"这个功能做完了"？
- 关键名词：**验收标准（Acceptance Criteria）**——可验证的完成定义
- 标准写法：每条都是"当____时，应该____"，可以被测试验证

**⑦ 里程碑**
- 人话：分几期交付？每期做什么？
- 关键名词：**里程碑（Milestone）**、**迭代（Iteration）**——一轮一轮的周期

**⑧ 明确不做**
- 人话：划边界，什么功能**这一版不做**（防止需求膨胀）
- 这是最容易被忽视也最重要的一节：写清楚"不做"比"做"更能保护项目

### 2.3 标准做法：需求评审会

PRD 写完，产品经理召集设计、开发、测试开会，逐条过 PRD：
- 开发评估"这个功能技术上可不可行、要多久"
- 测试确认"这个验收标准能不能测"
- 有争议当场拍板，改完文档再开发
- 评审会的本质：**让所有人开工前对齐同一张图纸**

### 2.4 标准做法：优先级体系

| 级别 | 含义 | 人话 | 判据 |
|---|---|---|---|
| **P0** | Must-have | 没有它产品不成立 | "没有这个功能，痛点就解决不了" |
| **P1** | Should-have | 应该有，没有也能凑合用 | "没有会难受，但能用" |
| **P2** | Could-have | 锦上添花 | "以后有精力再做" |

配套法则 **MoSCoW**：Must（必须）/ Should（应该）/ Could（可以）/ Won't（这版不做）——和 P0/P1/P2 大致对应（MoSCoW 多一级 Won't"这版不做"，P 体系里没有对应项）。

### 2.5 专业名词

| 名词 | 全称 | 人话 |
|---|---|---|
| PRD | Product Requirements Document | 产品需求文档，项目的宪法 |
| MRD | Market Requirements Document | 市场需求文档，论证"这个市场值得做"（大公司用，个人项目不需要） |
| BRD | Business Requirements Document | 商业需求文档，论证"这生意能赚钱"（大公司用） |
| 用户故事 | User Story | 用固定句式描述需求："作为一个____，我想____，以便____" |
| 验收标准 | Acceptance Criteria | "做到什么程度算完"的可验证标准 |
| MVP | Minimum Viable Product | 最小可行产品，先做最核心的 |
| 竞品分析 | Competitive Analysis | 研究市面上同类产品怎么做的，取其精华避其坑 |
| 需求变更 | Requirement Change | 开发中改需求——越晚变更代价越大 |
| 痛点 | Pain Point | 用户难受的地方 |
| 使用场景 | Use Case | 用户在什么情况下用 |
| 迭代 | Iteration | 一轮一轮的开发周期 |

### 2.6 常见误区

- ❌ **把"我想要的功能"当成"用户需要的功能"**——需求的第一来源是痛点，不是灵感。
- ❌ **PRD 写成 100 页**——个人项目 3-5 页足够，写清楚上面八节即可。
- ❌ **只写"做什么"不写"验收标准"**——没有验收标准，开发说"做完了"、测试说"没做完"，永远扯不清。
- ❌ **需求评审走形式**——评审是为了提前发现"理解不一致"，不是过场。

### 2.7 需求管理与项目管理（需求到开发的衔接）

PRD 写完不是直接扔给开发，中间还有一套"翻译和调度"的工作——**项目管理（Project Management）**：

| 名词 | 人话 |
|---|---|
| 需求池 Backlog | 所有待做功能的"排队名单"，按优先级从上往下排，做完一个划掉一个 |
| 任务拆解 Task Breakdown | 把 PRD 里一个功能拆成若干可执行的小任务（"做登录页"拆成"画界面/写校验/接接口"） |
| 排期 Scheduling | 估算每个任务要多久，排出时间表 |
| 估时 Estimation | 估算任务工时的动作（单位常用"人天"；敏捷团队用 **Story Point 故事点**——相对大小的抽象单位） |
| Sprint 冲刺 | 敏捷开发的"一个工作周期"（通常 1-2 周），周期开始时挑任务进冲刺，结束时要交付可用成果 |
| 需求管理工具 | 管 Backlog、排期、进度用的软件：**Jira**（行业标准，复杂）、**Trello**（看板式，简单）、**Linear**（新一代，简洁）、飞书多维表格（国内常用） |
| 看板 Kanban | 把任务卡片拖来拖去的可视化板子：待办 → 进行中 → 已完成 |

**为什么需要这一层？** 因为"人话的需求"和"代码的任务"粒度不同：PRD 说"做一个登录功能"，开发需要的是"今天做页面、明天做校验、后天联调"。拆解和排期就是这道翻译工序。个人项目的简化版：把 PRD 拆成里程碑清单，用台账文档跟踪"已做/待做"——这就是"做一步记一步"的由来。
