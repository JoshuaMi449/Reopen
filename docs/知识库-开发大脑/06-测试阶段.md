## 第 6 章：测试阶段（QA 的世界）

### 6.1 是什么

测试阶段回答一个问题：**"这东西到底对不对？"**

外行以为测试是"开发完了点一点"，正规团队的测试从写代码第一天就开始了，而且是**分层的**——这就是著名的**测试金字塔（Testing Pyramid）**：

```text
         /\        UI 测试（少而精）：模拟真人点界面走全流程
        /  \       端到端测试 E2E：全链路串起来测
       /----\      集成测试：模块之间拼起来测
      /------\     单元测试（最多）：单个零件单独测
```

| 层级 | 名词                         | 人话                                         | 谁写       |
| ---- | ---------------------------- | -------------------------------------------- | ---------- |
| 底层 | 单元测试 Unit Test           | 测单个零件：这个函数输入 2+2 必须返回 4      | 程序员     |
| 中层 | 集成测试 Integration Test    | 零件拼起来测：登录模块和数据库模块配合对不对 | 程序员     |
| 高层 | 端到端测试 E2E（End-to-End） | 模拟真人完整走一遍："注册→登录→下单→付款"    | 自动化脚本 |
| 顶层 | UI 测试                      | 模拟点击界面元素（自动点按钮填表单）         | 自动化脚本 |

### 6.2 标准做法：测试的配套名词

| 名词                                    | 人话                                                               |
| --------------------------------------- | ------------------------------------------------------------------ |
| 测试用例 Test Case                      | 一条"输入什么 → 期望什么"的检查项（如"输入空用户名→提示不能为空"） |
| 断言 Assertion                          | 测试里的判定句："结果必须等于 4，否则算失败"                       |
| 覆盖率 Coverage                         | 代码有多少比例被测试跑过（80% 是常见及格线）                       |
| 回归测试 Regression Test                | 改完代码后，把老测试全部重跑一遍，确认没改坏旧功能                 |
| 冒烟测试 Smoke Test                     | 上线前快速点一遍核心流程，"能不能开机的检查"                       |
| 手动测试 / 自动化测试                   | 人肉点 vs 脚本自动跑；能自动化的优先自动化                         |
| 测试环境 Staging                        | 假的生产环境，上线前先在这里全量演练                               |
| 生产环境 Production                     | 用户真正用的环境，神圣不可轻易动                                   |
| Bug / 缺陷                              | 产品的毛病；Bug 有完整生命周期：**报告→复现→修复→验证→关闭**       |
| 验收测试 UAT（User Acceptance Testing） | 最后一步：**让真实用户（或产品方）亲手验收**，说行才上线           |

### 6.3 常见误区

- ❌ **"开发自测过就行"**——写代码的人自带盲区，自己永远测不出自己的错。
- ❌ **只测正常情况**——真正的 bug 都在边界：空输入、超大文件、断网瞬间、快速连点。
- ❌ **修一个 bug 不跑回归测试**——按下一个葫芦浮起一个瓢是常态。
- ❌ **UAT 走形式**——产品方不亲手用就点头，上线后全是你自己买单。

### 6.4 测试的常用辅助手段

| 名词                         | 人话                                                            |
| ---------------------------- | --------------------------------------------------------------- |
| Mock 假数据                  | 测试时用"假的后端/假的数据"顶替真家伙——真接口没写好也能先测前端 |
| 压测（性能测试）Load Testing | 模拟大量用户同时使用，看系统扛不扛得住（如"1 万人同时下单"）    |
| 性能剖析 Profiling           | 用工具测量程序每一段花了多少时间，找出最慢的那段                |

### 6.5 测试技巧（思维框架）

**怎么想出测试用例**：两个经典框架——

| 框架       | 人话                                     | 例子（登录表单）                                     |
| ---------- | ---------------------------------------- | ---------------------------------------------------- |
| 边界值分析 | 错的都在边界上：空、最长、刚好超限       | 空用户名 / 1 个字符 / 100 个字符（上限）/ 101 个字符 |
| 等价类划分 | 把输入分成"等效的几组"，每组抽一个代表测 | 合法手机号测一个即可，不用测一千个                   |

**测试替身（假演员）的区别**：

| 替身      | 人话                                                             |
| --------- | ---------------------------------------------------------------- |
| Stub 桩   | 假数据源：只返回预先写好的答案（"查天气永远返回 25 度"）         |
| Mock 模拟 | 会记账的假演员：不仅返回答案，还记录"被调用了几次、用了什么参数" |
| Spy 间谍  | 真演员+监听器：真的执行，但偷偷记录行为                          |

**TDD（测试驱动开发）**一句话：先写测试（红）→ 再写代码让测试通过（绿）→ 再清理代码（重构）。AI 辅助开发时可以让 AI 遵循这个循环，质量明显更稳。
