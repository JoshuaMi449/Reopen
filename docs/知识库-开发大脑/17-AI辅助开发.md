## 第 17 章：AI 辅助开发（vibe coding 的正规军打法）

### 17.1 是什么

**AI 辅助开发**（俗称 vibe coding）= 用 AI（如 Claude Code）当主力开发者，人来当产品经理和验收员。前面各章讲的是"正规团队怎么分工"，本章讲的是**人和 AI 怎么配合**：你负责"做什么、好不好"，AI 负责"怎么做"。

核心分工原则（全文最重要的一句）：**AI 干活，你做判断。**

### 17.2 给 AI 布置任务

AI 最怕的不是复杂的活，是**模糊的活**。布置任务说清四件事：

| 要素 | 人话           | 差描述 vs 好描述                                                |
| ---- | -------------- | --------------------------------------------------------------- |
| 背景 | 现在是什么情况 | ❌"帮我修一下 bug" ✅"点击删除按钮后应用闪退，删除其他项目正常" |
| 目标 | 做完是什么样   | ❌"把界面做好看点" ✅"把按钮改成蓝色、圆角、悬停变深"           |
| 边界 | 什么不要动     | ❌ 不说 ✅"只改这个文件，其他别动"                              |
| 验收 | 怎么算完成     | ❌ 不说 ✅"改完你自己跑一遍测试，把结果贴给我"                  |

**让 AI 先讲方案再动手**：复杂任务先让 AI 说"我打算怎么做、要动哪些文件"，你点头再让它执行——这比做完返工便宜十倍。

### 17.3 验收 AI 的产出

AI 交活的当下是**最不可信**的时刻（幻觉高发）。验收四步：

1. **跑起来看**：能跑 ≠ 对，但跑不起来一定不对
2. **看它动了哪些文件**：改的范围和任务相符吗？（改了没让动的地方是坏味道）
3. **让它解释**："你这里为什么这么写？"——AI 解释不清的地方往往就是糊弄的地方
4. **对照验收标准**：任务布置时的验收标准，逐条打勾

人话：把 AI 当**新来的实习生**——能力强但要盯着交付，信任要逐步建立。

### 17.4 AI 出错怎么办

| 情况       | 应对                                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| 报错       | 把完整报错贴回给 AI（不要只贴半句），让它自己诊断——大多数报错 AI 一眼就能认出来                          |
| 越改越坏   | 立刻叫停，说"回退刚才的改动"，让它用 Git 恢复；再复盘"问题出在哪一步"                                    |
| 反复修不好 | 换思路：让 AI 先解释它认为的根因，再针对根因出方案；或开新会话重述问题（旧会话可能被错误思路带偏）       |
| 偷偷改方案 | 发现 AI 没按确认过的方案做 → 严肃指出，让它对照方案说明偏差原因。**严禁默许**（AI 会记住"偏离可以接受"） |

### 17.5 会话与上下文管理

AI 的"记忆"分两种：会话内上下文（会满）和持久记忆（有限）。管理要点：

- **一个会话干一件事**：跨任务会话会积累大量无关内容，挤掉关键信息
- **新会话要交代背景**：新会话的 AI 不知道前面聊过什么——用一句话交代"我们在做什么项目、现在进展到哪、这个任务要什么"
- **重要结论写进文档**：AI 的"记住"不可靠，可靠的记忆是**文件**（这就是知识库和台账存在的意义）
- **长任务中途让 AI 总结**：会话太长时让 AI 先总结"目前进度和下一步"，再继续

### 17.6 AI 幻觉的防御

幻觉 = AI 一本正经地胡说（编造不存在的 API、错误的命令、虚假的"事实"）。防御手段：

| 手段         | 做法                                                                |
| ------------ | ------------------------------------------------------------------- |
| 要出处       | "这个说法有出处吗？把链接/文档贴出来"——给不出处的断言存疑           |
| 让它自验     | "你刚才写的代码，自己检查一遍有没有问题"——AI 自查经常能抓出自己的错 |
| 关键结论复核 | 涉及删数据、付款、发布这类不可逆操作，**必须人肉复核**              |
| 小步交付     | 让 AI 一次做一小块，做完验收再做下一块——幻觉的破坏范围被锁小        |
| 跑起来验证   | 代码对错，跑一遍见分晓——让 AI 自己运行验证是最高效的防幻觉手段      |

### 17.7 Agent 与 MCP 的原理

**Agent**（智能体）= 会自己调用工具的 AI。普通对话 AI 只会"说"，Agent 会"做"：读文件、跑命令、搜网络、调 API，把结果带回来继续推理。

**MCP**（Model Context Protocol）= 给 AI 接工具的**标准插座**。装了某个 MCP 服务器，AI 就获得对应能力（搜网络、读写飞书、操作 GitHub）。

- 人话：AI 是大脑，MCP 是手。接的手越多，能干的活越多
- 选型原则：**按需装**——多一个 MCP 就多一份配置和出错面，用不到的不装
- 风险：AI 调用工具时可能误操作（删错文件、发错消息）——所以给 AI 的工具权限要克制，不可逆操作让 AI **先请示再执行**

### 17.8 给 AI 的行为规范（本项目语境）

以下规范来自本项目长期协作的实际要求，AI 在本项目中应当遵守：

| 规范         | 内容                                                                                 |
| ------------ | ------------------------------------------------------------------------------------ |
| 决策先确认   | 涉及方案选择、删除、发布等动作，**先说明打算，经确认后再执行**；不擅自改已拍板的方案 |
| 白话解释     | 面向非程序员用户，技术概念一律用人话+生活类比讲明白，直到用户说"懂了"                |
| 务实优先     | 规则贴合实际业务，"尽量"优于"禁止"；不为完美牺牲进度                                 |
| 做一步记一步 | 每完成一步在项目台账（文档 B）登记；每变更决策记变更日志                             |
| 改动可追溯   | 每次改动说明"改了什么、为什么"，范围只限于任务要求，不顺手改无关内容                 |

### 17.9 常见误区

- ❌ **把 AI 当神**——不验收、不复核、盲信输出。AI 的产出质量取决于你布置和验收的质量
- ❌ **把 AI 当黑盒**——不要求解释、不追问原理。你从 AI 身上学到的远比你让它干的多
- ❌ **一次让 AI 干太多**——需求堆成山，出错时无法定位是哪块的锅
- ❌ **放弃 Git**——有 AI 就不管版本管理。AI 改坏代码时，Git 是你唯一的后悔药
- ❌ **人完全不动脑**——"AI 说行就行"。产品判断（做什么、好不好用）永远是你的事，AI 替代不了
