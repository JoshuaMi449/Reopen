## 第 8 章：发布阶段

### 8.1 是什么

发布回答一个问题：**"怎么把成品送到用户手里？"**

### 8.2 标准做法

| 名词                          | 人话                                                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 打包 Build                    | 把源码加工成可安装/可运行成品                                                                                    |
| 发布 Release                  | 成品正式对外提供下载/更新                                                                                        |
| 分发渠道 Distribution Channel | 送到用户手里的路径：**应用商店**（App Store 等，要审核）/ **官网下载** / **GitHub Releases**（开源项目标准渠道） |
| 灰度发布 Gray Release         | 先放给 1% 用户试，没问题再全量——"小范围试水再放开"                                                               |
| 回滚 Rollback                 | 新版出大问题，一键退回上一个版本                                                                                 |
| A/B 测试                      | 同一功能做两个版本，随机分给两组用户，看数据定胜负                                                               |
| Changelog 更新日志            | "这一版改了什么"的说明文档                                                                                       |
| 版本冻结 Freeze               | 发布前几天禁止乱改代码，保证发的是测过的那个版本                                                                 |
| 热修复 Hotfix                 | 上线后发现紧急 bug，跳过常规流程火速发一个小补丁版                                                               |

### 8.3 开源项目的发布标准姿势

1. 代码推上 GitHub（main 分支稳定）
2. 打 Tag（v1.0.0）
3. 创建 Release：写更新说明 + 上传安装包（dmg/exe）
4. 用户从 Release 页下载安装

### 8.4 常见误区

- ❌ **发布前不冒烟测试**——把"点两下就崩"的版本发出去，口碑一次清零。
- ❌ **Changelog 写"修复若干问题"**——等于没说。写清楚"新增什么、修复什么"。
- ❌ **不做回滚预案**——上线前先想好"万一崩了怎么退"。

### 8.5 发布策略的决策框架

**签名与公证：值不值得花钱？**

| 选择          | 成本       | 用户看到什么                           | 适合                                |
| ------------- | ---------- | -------------------------------------- | ----------------------------------- |
| 不签名        | 0          | 双击弹"无法验证开发者"，需右键强制打开 | 自己用、内测阶段                    |
| 自签名        | 0          | 同上（警告略不同）                     | 开源项目初期，README 写清"如何打开" |
| 正式签名+公证 | 99 美元/年 | 双击直接开，更新也顺                   | 有真实用户、想上正式分发            |

判据：**当"用户打开时的摩擦"开始流失用户时，就值得花这 99 美元**——之前都不急。

**灰度发布的三兄弟**（容易混）：

| 策略       | 人话                                                         |
| ---------- | ------------------------------------------------------------ |
| 灰度发布   | 同一版本先放 1% 用户，看数据再逐步放量                       |
| 蓝绿部署   | 两套环境：蓝在服务、绿在待命；新版本上绿，验证 OK 一键切流量 |
| 金丝雀发布 | 新版本只给少数"哨兵"用户先尝，出问题只影响小部分人           |

人话：三者都是"小范围先试"，区别在"试的对象"——灰度按比例放量、蓝绿按环境切换、金丝雀按用户选哨兵。
